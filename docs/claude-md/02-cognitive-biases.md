## AI特有の認知の癖と対処（2026-09-07追記）

上の10項目は「何を確認するか」の手順だが、こちらは「なぜAIがその手順を飛ばしがちか」という
一段深い話。人間ならまず犯さない失敗の型をディープリサーチで調査し、このキット自身の実損
（`site/learnings/`に記録済み）で裏取りして5類型に確定した。新しい基盤・新しいGateは増やさない
——上の10項目を実行するときに、自分がどの癖に該当しやすいかを自覚するための地図として使う。

1. **ゼロコスト・コピペ症候群**: 人間はタイピング量・将来の面倒さで無意識に統合したくなるが、
   AIは2箇所目を書く心理的抵抗がゼロ。基準⑤⑥⑦（共通化サイン）は主にこの癖への対処。
2. **既視感なきタスク遂行**: 各タスクを独立文脈として処理し、「前にも見た気がする」という
   直感が働かない。`templates/diagnostics/check-near-duplicates.mjs`はこの欠如を機械で補う道具。
3. **推論で検証を代替する**: 「コードを読んで筋が通る」で実行時の確認を省略する。基準③
   「完膚なきまでの裏取り」・[`_docs/runtime-truth-verification-knowledge-base.md`](../../_docs/runtime-truth-verification-knowledge-base.md)はこの癖への対処。
4. **性善説の登録簿依存**: 「文書に書いた」「登録した」を「機能している」と同一視する。
   証明3点台帳・各`check-*.mjs`が「確認した証拠」を機械検査するのはこの癖への対処。
5. **「似ている」の解像度が粗い**: 表層的な類似・非類似だけで即断し、設計意図まで遡らない。
   `check-shared-parts-used.mjs`（事実＝同名関数）と`check-near-duplicates.mjs`（推測＝似た塊）を
   意図的に分離しているのはこの癖への対処——解像度の粗い1つの検査に混ぜない。

対処の基本形はどの類型も同じ: **「たぶん大丈夫」を機械検査に置き換える**。文章のルールを
増やすだけでは効かない（実例は`site/learnings/`の「証拠が無ければ完了扱いにできない仕組みにした話」
「文章のルールを機械検証可能な台帳へ格上げした記録」参照）。

### ★新しいルールを書いたら、その場で機械検査化を検討する（2026-09-14追記）

上の対処の基本形（「たぶん大丈夫」を機械検査に置き換える）は繰り返し書かれているのに、
実際には**新しいルールを追記した瞬間には実行されず、後から気づいて手直しする**ことが
このキット自身で複数回起きた:

- 並列セッション協調プロトコル（Main-Write Pause）が文章化されているだけで6日以上
  機械検査が無く、そのままこのセッション自身が手順違反を起こした（`.agent/coord.md`を
  commit直前ではなくcommit後になって初めて確認した）
- `_docs/DESIGN-approved-action-ledger-2026-09-08.md`（確定事項の実行し忘れを防ぐ設計）が
  完成から6日間、一切実装されず放置された

★**「ルールを機械検査に置き換えるべき」という原則自体は既に書いてある。足りないのは
『書いた直後にその場で検討する』という実行のトリガーだった。** 新しい基盤・新しいGateは
増やさない——既存の5類型・基準⑤⑥⑦と同じく、**判断の型を1つ足すだけ**にする。

**手順（CLAUDE.md・`docs/ai-rules/`へ規範的な文章「〜しないこと」「〜する」を書いたら、
書いたその場で自問する）:**

1. **違反を客観的事実として検出できるか？**（ファイルの存在・実行ログ・git差分等）
   → できるなら`templates/diagnostics/check-*.mjs`を作る候補にする
   （実例: `check-near-duplicates.mjs`＝似たコード塊という静的解析可能な対象、
   `check-shared-parts-used.mjs`＝同名関数の存在という事実ベースの検出）
2. **検出に自然言語理解や意味判断が必要か？**（「依頼文言が丁寧か」「本当にそのバグの
   証拠か」等）→ 無理に全自動化しない。`check-decision-receipt.mjs`のように
   **「判断そのもの」ではなく「判断を記録したかという事実」だけ**を機械化する
   ハイブリッド型を検討する（Semantic Judgmentは人間/AIに残す）
3. **どちらも無理なら、「なぜ機械化できないか」を一言添えて明示する。** 黙って
   文章のまま放置しない。将来同じ問題（実損）が再発したときに再検討する対象だと
   分かる形にする

★格上げされやすいのは「判定対象を客観的事実に絞り込めるもの」、されにくいのは
「セッション間協調のタイミング」や「人への依頼文言の適切さ」のような自然言語的判断が
絡むもの——という傾向がある（このキットの既存実装から見える経験則。断定はしない）。

★★**この節自身が「AIの自己申告」に依存しており、性善説の登録簿依存パターンの
未対処ケースだった（2026-09-24発覚）**。後述「AIへのお願い（守ること）」節の
「あらゆる調査を尽くす」「裏取り徹底」「MCP実操作確認」の3ルール（2026-09-24追加）は、
上記2番（自然言語判断が絡む）に該当するため機械検査化していない——だが、その
「機械化できない理由の明示」自体がこの節に無かった。ここに明示する。
call-before-ask heuristic（AskUserQuestion呼び出し前に調査系ツールの使用履歴を
非ブロッキングで警告する案）を検討したが、プロトタイプ検証なしに本採用していない。
