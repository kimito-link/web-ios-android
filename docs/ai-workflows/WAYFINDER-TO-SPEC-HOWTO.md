## council-fableとの使い分け(重要・最初に読む)

| | council-fable | wayfinder→to-spec |
|---|---|---|
| 向いている題材 | ゼロから理想を設計したい・複数案を比較したい・「最高の◯◯」 | **既存コードの真因を特定してから直す**バグ修正・機能追加 |

| 地図/素材の質を決めるもの | 会議メンバーの発散+司令塔の統合 | **司令塔による実コード裏取りの深さ** |
| 典型的な入口 | 「〈お題〉を3段構えで進めて」「最高の◯◯を設計したい」 | 「まず地図を作って」「wayfinderで進めて」「真因を特定してから直して」 |

**判断に迷ったら**: 「このバグ/機能は、既存コードのどこかに構造的な真因があるか？」と自問する。
YESならwayfinder→to-spec。単に新しい体験をゼロから考えたいならcouncil-fable。
両方が必要な題材(真因調査+理想像の再設計)は、まずwayfinderで地図を作り、その地図を

## 手順1: 地図(wayfinder)を作る

**コードは一切変更しない。** 対象機能に関係する箇所を実際に読み、以下の構成でmdファイルに書く。
ファイル名は `<お題>-MAP.md`(リポ直下、または横断お題ならgithub直下)。

### 地図に含めるもの(7項目)

1. **入口になる画面・コマンド・API** — ユーザーがどこからこの機能に触れるか
2. **関係する主要ファイルと責務** — 表形式で「ファイル: 責務」を短くまとめる
3. **データが流れる順番** — 呼び出し元→中間処理→描画、まで実際のファイル:行番号付きで追う
4. **既存の設計判断と、その根拠** — 過去のコミット・メモリ・コメントに残っている「なぜこうなっているか」。壊してはいけない境界はここに集約する
5. **変更すると壊れうる箇所** — 共有関数・drift防止契約・既存テストが依存する公開API
6. **未確認の前提と、追加調査が必要な点** — 実際に確認できなかったことは「推測」と明記して残す(嘘をつかない)
7. **実装前に決める必要がある質問** — 仕様化の際にFableに答えさせるべき論点をここで洗い出しておく

### 地図作成のやり方

- `Grep`/`Read`/`Glob`で実コードを読む。必要なら`Explore`エージェント(read-only・広い探索向け)に委譲してもよいが、**司令塔が結果を裏取りしてから地図に書く**(サブエージェントの報告を鵜呑みにしない)。
- 事実には必ず `[file.js:123](path/to/file.js)` 形式でファイル:行番号を付ける。推測は「推測」「未確認」と明記する。
- 既存のメモリ(`memory/*.md`)・過去のHANDOFF・design docに「なぜこの設計になったか」が書かれていることが多い。見つけたら引用し、`[[memory-slug]]`でリンクする。

### 地図のセルフチェック(書き終えたら必ず自己点検)

- [ ] ファイル名の列挙だけで終わっていないか(「なぜここを通るか」まで書けているか)
- [ ] 既存仕様を守る理由が書かれているか
- [ ] ユーザー体験上の制約が書かれているか
- [ ] データ保存・互換性・失敗時の挙動が含まれているか
- [ ] 調査で確認した事実と、まだ未確認の推測が分かれているか
- [ ] 重要な判断へ、ファイル・commit・メモリなどの根拠が付いているか

足りない項目があれば、コード変更を始めずに追加調査する。

## 手順2: 地図から仕様(to-spec)を作る

`Agent`ツールで`model: "fable"`を指定し、地図をFableに渡して実装仕様を書かせる。

> **Fableの使いどころの正本は [`FABLE-3STEP-HOWTO.md`](FABLE-3STEP-HOWTO.md)**（2026-08-23 方針確定）。
> 要点だけ再掲: ①**Fableにコードを書かせない**（設計・仕様まで。実装は手順3で別モデル）
> ②**会議ハーネスにFableを入れない**（外から裁定させるから価値が出る）
> ③**Fableが使える環境では必ず手順2を委譲する**（「Opusでも書けるから」で省略しない）。

### Fableに必ず渡すもの

- 地図のフルパス、または地図の全文
- 「新しい事実を推測で補わず、未決定事項は質問として残してください」という指示
- 地図6章(実装前に決める必要がある質問)への回答を必ず含めるよう明示指示

### 仕様に含めるもの(7項目・Matt Pocock氏の型)

1. **Problem Statement** — 何が問題か、なぜ問題か(ユーザー体験への影響)
2. **Solution** — 採用する解決アプローチとその理由。地図6章の質問全てに明確に答える(推測でなく設計判断として)
3. **User Stories** — 正常系だけでなく次を含める: 空の状態・読み込み中・失敗と再試行・権限不足・古いデータとの互換性・Undo/Cancel/Back・別画面/別ウィンドウとの競合
4. **Implementation Decisions** — ファイル名・関数名・引数レベルの具体案。新しい関数を作るなら関数シグネチャまで
5. **Testing Decisions** — どの層をどう確かめるか。テストケース名まで具体的に(既存のテスト流儀に沿わせる)
6. **Out of Scope** — 今回やらないことを明言する(エージェントが善意で仕事を広げるのを止める境界)
7. **Further Notes** — 実装時の地雷・注意点

最後に「未解決の質問」と「仕様に根拠がない断定(assumption list)」を一覧にさせる。

Fableの最終メッセージ全体がそのまま仕様書になるよう指示する(前置きの挨拶等は不要)。

### 仕様の裏取り(司令塔の役目・省略しない)

Fableが挙げたファイルパス・行番号・「既存関数は◯◯している」という主張は、**司令塔が実コードで
裏取りしてから採用する**。Fableが「未確認」とした論点も、司令塔が追加でコードを読めば解決できる
ことがある(実例: venue-ranking-churn案件で、Fableが「count減少経路の実在は未確認」とした点を
司令塔が`pruneRoster`の実装を読んで確認し、仕様に追記した)。

### 仕様の最終レビュー(3視点批判・書き終えたら必ず自己点検)

実装者・テスター・利用者の3つの視点で仕様を批判する。確認すること:
- 根拠のない断定
- 地図と矛盾する判断
- 抜けている失敗時の挙動
- テストできない曖昧な表現
- 非スコープに入れるべき拡張
- セキュリティ・権限・個人情報の見落とし
- 既存データや既存ユーザーへの影響

確認できないことは推測せず「未確認」と明記する。

## 手順3: 実装は別モデル(今はやらない・引き継ぎ)

1. 設計を**正本md**に保存(`<お題>-SPEC.md`)。冒頭に「設計=Fable / 地図・裏取り=司令塔 / 日付」を明記し、地図へのリンクを張る。
2. **実装ハンドオフmd**(`<お題>-IMPLEMENTATION-HANDOFF.md`)を書く。**この1枚だけで着手できる**粒度で: スコープ(MVPだけ)・着手手順(ブランチ+TDD)・実装ステップ(仕様の該当章を指す)・機械的な完了判定・地雷。
3. 非自明だった事実はメモリに記録(project型)。
4. 実装は明示的に指示されるまでは**やらない**。「次チャットで実装ハンドオフを読ませ、ブランチを切って実装」と案内して終える。

### 実装する場合(指示があれば)

- ブランチを切ってTDDで着手。
- 実装後は**reality-checkerに検証を委任**(自己採点しない)。仕様書の「Testing Decisions」章がそのままreality-checkerへの検証依頼の土台になる。
- 変異テスト(該当ロジックを一時的に壊す→テストが赤くなることを確認→復元)で、テスト自体の実効性も確認する。
- `npm run verify:cc`(またはプロジェクト固有の出荷ゲート)を通してからcommit。

## ベストプラクティス & 地雷

- **地図は司令塔が書く(丸投げしない)**: サブエージェントに地図を書かせる場合も、ファイルパス・行番号・「既存関数はこうなっている」という主張は司令塔が実コードで裏取りしてから採用する。ここを省略すると、幻覚が地図→仕様→実装まで伝播する。
- **仕様書の長さは品質の指標ではない**: 間違った前提を長文化しても間違った仕様書ができるだけ。「Testing Decisions」と「Out of Scope」が独立して存在するかを重視する。
- **設計時レビューと実装後検証はセットで**: 仕様書段階の3視点批判だけで満足せず、実装後にreality-checker(または同等の独立検証)にかける。どちらか一方では足りない。
- **正本を散らさない**: このHOWTO本文のコピーを作らない。各リポには橋渡し1行だけ。
- **fail-closed**: 分からなければ止める・黙って成功にしない。未確認は「未確認」と書く。
- **地図とcouncil-fableの会議素材は共存できる**: 地図を先に作り、その地図を会議ハーネスの問い(council-question.txt)の材料として使ってもよい。両方式は排他ではない。
