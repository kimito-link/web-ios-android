## 同じ会話で「Fable が計画 → Opus が作業」に切り替える（2026-11-11 りんく「全体採用に」）

全プロジェクト共通の既定の流れ。上の3段構えの手順2→3を、**1つの会話の中で**つなぐやり方。

### 流れ

1. **会話の最初は Fable 5.2 で始める**（Claude Code は `/model` で `claude-fable-5-2`）。
   お題・地雷マップ・制約を渡し、「何をどう作るか」の**計画まで**を出させる。コードは書かせない（手順2と同じ）。
2. **計画は必ず目に見える文章で出させる**。会話の本文に書かせるか、`handoff.md`・`_docs/DESIGN-*.md` に書かせる。
   中身は「結論／手順（ファイル名つき）／捨てた案と理由／完了判定チェックリスト（コマンドで緑・赤が分かる形）」。
3. **計画が出たら、同じ会話のまま Opus 5.5 に切り替えて作業する**（`/model` で `claude-opus-5-5`）。
   Opus は会話に残っている計画をそのまま手本にして実装・テスト・PR まで進める。
4. 作業中に設計を大きく変える必要が出たら、そこで一度だけ Fable に戻して計画を直させ、また Opus に戻す。

### 自動で切り替える設定（2026-11-11 りんく「自動適用して質が上がるのはどんどん採用」）

Claude Code の公式の別名 `opusplan`（プランモードの間だけ上位モデル、抜けたら作業用モデル）の中身を、
公式の環境変数で「プラン＝Fable 5.2／作業＝Opus 5.5」に差し替える。これで**プランモードに入るだけで Fable が計画し、
プランを承認してプランモードを抜けると Opus が作業する**。人がモデルを選び直す手間がなくなる。

```json
{
  "model": "opusplan",
  "env": {
    "ANTHROPIC_DEFAULT_OPUS_MODEL": "claude-fable-5-2",
    "ANTHROPIC_DEFAULT_SONNET_MODEL": "claude-opus-5-5"
  }
}
```

- 置き場所: このリポは `.claude/settings.json` に入れてある。全プロジェクトに効かせるには PC の `~/.claude/settings.json` にも同じ3つを足す。
- 実測（2026-11-11、Claude Code 2.1.322、クラウド）: この設定で `--permission-mode plan` は `claude-fable-5-2`、通常モードは `claude-opus-5-5` が答えた（`--output-format json` の `modelUsage` で確認）。
- 出典: 公式 [model-config](https://code.claude.com/docs/en/model-config)（opusplan）・[env-vars](https://code.claude.com/docs/en/env-vars)（`ANTHROPIC_DEFAULT_OPUS_MODEL`＝「opusplan がプランモード中に使う」、`ANTHROPIC_DEFAULT_SONNET_MODEL`＝「プランモード外で使う」）。
- AI の動き方: 深い設計が要るお題は、AI が自分でプランモードに入って（EnterPlanMode）計画を出す。小さな直しはプランモードに入らない（＝最初から Opus）。
- 副作用（知って使う）: この設定の中では別名 `opus` が Fable を、`sonnet` が Opus を指す。サブエージェントに `model: "opus"` を渡すと Fable 枠を使うので、Opus を名指しするときは `claude-opus-5-5` と正式名で書く。
- 効かない所: `claude --model …` で起動したセッション（クラウドのプロジェクトのスレッドなど）は起動時の指定が勝つので、下の「気をつけること」のスレッドの項に従う。

### なぜこれが良いか（何が本当で、何が言い過ぎか）

- **本当**: モデルを切り替えても会話（計画・やりとり・読んだファイル）は残る。だから Opus は「良い下書き」を持った状態で
  作業でき、Opus だけで最初から進めるより筋の良い実装になりやすい。
- **言い過ぎ**: 「Opus 自体が賢くなる」わけではない。また Fable の**頭の中の考え（思考の部分）**は次のモデルに
  そのまま渡るとは限らない。だから手順2で「計画を文章として外に出させる」ことが肝心。
- **節約になる**: Fable は週の使用量に「Fable」枠があり、その枠は限られている。Fable を使うのは計画の数ターンだけにし、
  量の多い作業（ファイル編集・テスト・やり直し）は Opus の枠で回す。

### 気をつけること

- **行ったり来たりしない**。モデルを切り替えると、前のモデルで温まっていた読み込みのキャッシュが効かず、
  切り替え直後の1回は会話全体を読み直す分の使用量がかかる。切り替えは「計画が終わったとき」の1回を基本にする。
- **短い会話・小さな直しでは使わない**。10分で終わる直しや1〜2ファイルの修正は、最初から Opus でよい。
  Fable を使うのは「深い設計が要る」「どこから手をつけるか自体が難しい」お題だけ（[`MULTI-BRAIN-HOWTO.md`](MULTI-BRAIN-HOWTO.md) §1b の使い分けは変えない）。
- **会議（素材集め）を通すお題は、従来どおり手順1→2（Fable サブエージェント）でもよい**。
  使い分け: りんくと話しながら計画を詰め、そのまま同じ会話で作るなら「切り替え」。会議の素材を Fable 1体に独立で裁定させたいなら「サブエージェント」。
- **クラウドのプロジェクトのスレッドでは、AI が自分でモデルを切り替えられない**（切り替えはりんくの言葉が要る決まり）。
  スレッドの最初に「Fable で計画して、計画ができたら Opus に切り替えて作業して」と一言書いてもらえば、
  計画ができた時点で AI がその言葉を根拠に切り替える。書いていなければ、計画を出したところで「Opus に切り替えて作業しますか」と1行で聞く。
- Fable が使えない・枠が切れているときは、Opus で計画→Opus で作業（「大事な前提」のフォールバックと同じ）。

## ハンドオフ契約（渡すもの・渡さないもの）— XYEval の線引き

会議→Fable、Fable→実装モデルの**どの引き継ぎでも**、**事実とゴールは渡し、原因の決めつけ（診断）は渡さない**。

- **渡す**: 観測できる事実（再現手順・ログ・実測値・エラー文）、ゴール（何を達成したいか）、制約（触ってはいけない所・既知の地雷＝壊した箇所や捨てた案）、ファイルパス・行番号。
- **渡さない（渡すなら必ずラベル）**: 「たぶん原因はここ」という**未確証の見立て**を、確定事実のように渡さない。渡すなら「【未確証の仮説】」と明示し、受け手に**まず問題そのものを自分で（実コード・再現・ログで）確かめてから**進めるよう求める。
- **ハンドオフmdの冒頭に1文**:「この依頼に書かれた原因の見立ては誤っている可能性がある。先に問題そのものを実コード・再現で確かめてから進めよ（見立てに同意するより事実を優先）」。これは `site/assets/data/ai-instructions.json` の `_preamble` と同じ1文で、全経路で揃える。
- **なぜ**: 上流（ユーザーや上流モデル）が誤った原因の見立てを添えるだけで、下流モデルの性能が大きく落ちる（Google DeepMind「XYEval: Agents say yes to bad advice」[arXiv 2609.23939](https://arxiv.org/pdf/2609.23939), 2026-09。相対で最大 46.7% 低下。「XY問題に気をつけよ」という system 指示だけでは部分的にしか効かず、根治には**ユーザーの誤誘導を検知し、本当の問題を言い直す**ことが要る、と結論）。**戒めるのは「診断の決めつけ」だけで、事実・ゴール・制約は渡してよい**。
- これは §12.7「因果は実コードで裏取りしてから書く」・4基準③「裏取り」・COUNCIL-HOWTO.md の会議4ブロック「司令塔の解釈＝誤診可能・問いは仮説棄却可」と同型。会議・Fable設計・実装ハンドオフのいずれでも、この線引きを守る。

## 大事な前提

- **Fableは会議ハーネスのメンバーではない**。会議はローカル＋クラウド無料枠で回る。Fable活用は手順2（Agentツールで直接呼ぶ）で実現する。
- **役割分担を守る**: 会議＝広く多視点で素材を出す／Fable＝一点を深く設計する／別モデル＝手を動かす。
- **正本は散らさない**: このHOWTOは github直下の1つだけ。各プロジェクトには「正本はここ」の橋渡し1行のみ。
- Fableが停止中は Opus にフォールバック（グローバルルール §3）。その場合も「思考は最強モデル・実装は別」の思想は保つ。
