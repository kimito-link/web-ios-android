## ★問いの書き方（2026-08-18 追加・実測で効果を確認）

**観測と解釈を混ぜた1文を書かない。** 司令塔の見立てを事実の顔で書くと、会議は全員が
その枠内で回答し、真因に届かなくなる。次の4ブロックで書くこと。

```
【観測】
  エラー実文言・時刻・実測値・再現手順だけを並べる。
  動詞は「〜が出た」「〜だった」。「〜が死んだ」「〜が原因で」など因果を含む動詞は使わない。
  ★矛盾の材料になりうる観測を削らない（後述の実例では、これが真因到達の鍵だった）。

【司令塔の解釈】※誤診の可能性あり。観測と矛盾したら捨てること
  現時点の見立て。この注記を必ず添える。

【制約】
  予算・締切・変更禁止領域。

【問い】
  解釈の採否も回答者に委ねる形で書く。
  ×「Xをどう直すか」
  ○「観測を説明する真因は何か。Xという見立ての採否も含めて判断せよ」
```

### なぜこう書くのか（2026-08-18 の対照実験）

分類器が壊れた事件で、司令塔が「分類器のモデルが死んだ」という**誤診**を事実として
問いに書いた。同じ4体・同じ情報・同じ統合プロセスで、問いの書き方だけを変えて比較した:

| 条件 | 真因に届いた体 | 会議の最終結論 |
|---|---|---|
| A: 元の問い（解釈を事実として記載） | **0/4** | **誤診のまま確定**（「分類器を廃止してgeneral直行」という誤った処方） |
| B: 上のテンプレで観測/解釈を分離 | 1/4（lead役） | **真因に到達**（「フォールバック機構が動作していない」） |
| C: 元の問い + 「問いを検死せよ」指示 | **0/4** | **逆効果**（1体は指示を無視、1体は「問いの前提は観測と整合」と誤ったお墨付き） |

**効いたのはアンカーを外すこと**であって、プロンプトで「疑え」と命じることではない。
情報量の差ではない点が重要——元の問いにも矛盾の材料（フォールバック鎖の2番目に生存モデルが
居る）は書いてあった。4体は材料を持っていて照合しなかっただけである。

Bで真因に届いた1票は少数意見だったが、統合役が対立点として俎上に載せ、判定で採用した。
**1体でも枠を破れば、合議が拾う。**

注意: Cが示す通り「疑え」型の指示は偽の安心を生む（矛盾を見落としたまま「整合」と宣言する）。
critic の ROLE_DIRECTIVE に検死手順を足す案は、この実測を根拠に**見送っている**。

### 効く型・効かない型（2026-08-18 実会議3事例で検証）

テンプレは万能ではない。**実会議（4体並列＋批判＋統合）で3事例を A/B 比較した結果、到達率は 0/3 → 2/3**。

| 事例 | A: 誤診込みの問い | B: テンプレ適用 |
|---|---|---|
| 分類器が general に落ち続ける | 誤診のまま確定 | **真因に到達** |
| 同一デプロイでAPIとページが食い違う | 取得層の周辺を列挙するに留まる | **「取得層は機能している。境界の問題」と明言＝真因** |
| pnpm install は成功するのに build が落ちる | 到達せず | **到達せず** |

**効く型**: 問いの中に既に矛盾の材料がある誤診。
「APIでは6件・HTMLでは0件」「鎖の2番目に生存モデルが居るのに全落ち」のように、
観測同士が食い違っているのに照合されていない状態。テンプレはこの照合を促す。

**効かない型**: 環境を実測しないと到達できない真因。
pnpm の事例は「`find node_modules/.pnpm/<pkg> -type f | wc -l` が 0」という
ストアの実体を数えて初めて分かるもので、問いに書かれた観測だけからは論理的に導けない。
**こういう問いは会議に投げる前に、司令塔が手を動かして観測を増やすこと。**
会議は「材料の照合」はできるが「材料の採取」はできない。

#### キーの流し込み（これをやらないとクラウド勢が丸ごと欠ける）

APIキーは**User scopeの環境変数**に置いてあり、素で `node` を起動しても読めない。
PowerShellで User scope からプロセスへ流してから起動する（2026-08-25 実機で確認した手順）:

$names = (Select-String -Path scripts/meeting.mjs -Pattern 'process\.env\.([A-Z0-9_]+)' -AllMatches).Matches |
         ForEach-Object { $_.Groups[1].Value } | Sort-Object -Unique |
         Where-Object { $_ -notlike 'COUNCIL_*' -and $_ -notlike 'MEETING_*' }
foreach ($n in $names) {
  $v = [Environment]::GetEnvironmentVariable($n, 'User')
  if ($v) { Set-Item -Path "env:$n" -Value $v }
}

node scripts/meeting.mjs path\to\question.txt --out answers.json

## 複数PCでOllamaを分散する（2026-09-08追記）

**状態: 方針確定・コード変更不要と確認済み。実機側の設定はPC個別に必要（未実施）。**

`tsuioku-no-kirameki.com/scripts/meeting.mjs`は既に`OLLAMA_HOST`環境変数に対応済み
（`let OLLAMA = process.env.OLLAMA_HOST || 'http://127.0.0.1:11434'`の行、実測確認済み）。
スキームなし（`192.168.x.x:11434`）でも自動で`http://`を補うため、
**追加のコード変更なしに別PCのOllamaを呼べる**。

### 前提: OneDriveは使わない

複数PC間のファイル共有・連携は**OneDrive同期に頼らない**（PCが重くなるため。ユーザー方針）。
ここで説明する方式は、OneDriveを一切使わずネットワーク経由の直接通信だけで完結する。

### やり方

1. **LLMを動かす側のPC**（例: GPU搭載機、または常時稼働させたい専用機）で、Ollamaを
   外部から到達可能にする:
   ```powershell
   # そのPCのUser環境変数としてOLLAMA_HOSTを0.0.0.0にする（既定は127.0.0.1限定=外部から見えない）
   [Environment]::SetEnvironmentVariable('OLLAMA_HOST', '0.0.0.0:11434', 'User')
   # 設定後はOllamaを再起動（タスクトレイから終了→再度起動）
   ```
   Windowsファイアウォールで`11434`番ポートの受信を許可する必要がある場合がある。
2. **呼び出す側のPC**（司令塔Claudeが動いている側）で、会議実行時だけ環境変数を
   一時的に上書きする（Userスコープの既定値は変更しない——他の用途に影響するため）:
   ```powershell
   $env:OLLAMA_HOST = "http://<LLM側PCのIPアドレス>:11434"
   node scripts/meeting.mjs "<council-question.txtのフルパス>" --out "<出力先>"
   ```
3. **疎通確認**（会議を回す前に必ず先にこれで到達性を見る）:
   ```powershell
   curl -m5 http://<LLM側PCのIPアドレス>:11434/api/tags
   ```
   到達できなければ、同じネットワーク（Wi-Fi/LAN）に両方が繋がっているか、
   ファイアウォールで塞がれていないかを疑う。

### 使いどころの判断

- **GPU無し・非力なPC**: 会議参加は諦め、`ollama pull`済みの7B以下小型モデルの
  CPU推論専用機として、gmail-watch的な軽量常駐タスクの実行環境に回す方が現実的
  （大きいモデルのCPU推論は遅すぎて会議のタイムアウトに引っかかりやすい）。
- **GPU搭載PC**: そのPCのOllamaを`0.0.0.0`公開し、他のPC（非力なノートPC等）から
  会議のローカルメンバーとして呼ぶ構成が有効。
