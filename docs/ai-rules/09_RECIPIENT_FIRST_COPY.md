# 相手の得から書く Web の案内

今の到達点: 方針はここが正本。このリポジトリで文面を変えた面と、まだ変えていないプログラムは [`../../_docs/ROLLOUT-recipient-first-copy-2026-11-08.md`](../../_docs/ROLLOUT-recipient-first-copy-2026-11-08.md)。

伝え方の順番は、読み手がすでに持っている用事から始める。送り手の「登録してほしい」「買ってほしい」からは始めない。書籍の名前は調子の出典であって、本文の引用も、書籍どおりであるという主張もしない。

## 順番

1. 自分ごと。いま画面にある結果、持っている Web、出そうとしているアプリなど、相手がすでに見ているもの。
2. 得られること。その用事が、どう楽になるか、何を自分で決められるか。
3. 今と後の差。今開いているあいだに分かることと、閉じたり見送ったりしたときに残ること。損失は、測ったままであること、ストアにまだ出ないこと、更新作業が自分に戻ること、のように事実の範囲で書く。
4. 任意の次。リンクは下線付き。押さなくても、上の結果や説明は残る。

LINE は、その会話を置く場所であるときだけ書く。登録そのものを目的にしない。ページが結果を自動で送らないなら、そのことも書く。

## 補完（同じ用事のもう一つ）

主の選択が、同じ機会にもう一つ手間を残すときだけ、任意の二つ目を置く。二つ目は、その手間を同じ流れの中で片づける。高い段へ乗せ替えることや、関係の薄い商品を並べることは、ここでの補完ではない。

食べ物の組み合わせは、この区別のたとえである。利用者向けの文面に、その食べ物は書かない。

一緒にある利得は、商品ごとに一文で書く。

「人が支払いを見た直後は買いやすい」は、置く位置の仮説である。文面では事実として書かない。率も保証もしない。

## 書いてよい事実

- このリポジトリの表や設定にすでにある料金、範囲、見送り方。
- 診断シェルが実際にすること。結果は端末の中、次の確認日、カレンダーか端末内の知らせ、サーバーへは送らない。
- 運営者名は株式会社ベストトラスト。個人名は出さない。

数値を新しく足すときは、出典と、その数値が何を数えたものかを同じ場所に書く。出典が無い速さ、件数、割引、期限、残数は書かない。

## 出さない面

`distribution.surface` が `app` または `extension` のとき、および環境変数 `DISTRIBUTION_SURFACE` がそのどちらかのときは、紹介、有料、LINE の勧誘を描画しない。不明な面は app とみなす。正本は `templates/diagnosis-shell/surface-policy.mjs`。

Web でも、取次店コードや紹介コードの欄は足さない。

## 料金と購入

新しい価格、割引、定期課金、自動加算、初期選択の追加、黙って入るカートは作らない。既存の checkout が合計を計算できないページでは、合計を作ったことにしない。追加額は既存の表の額をそのまま書き、頼んだときだけ足すと書く。

解約や見送りは、今より手間を増やさない。アカウントの名義が相手に残る、月額を見送ると更新作業が相手に戻る、のように既存の契約範囲を短く書く。

購入完了メールの送信文と、配信シナリオの本文は、実在の補完商品と URL と料金がそろうまで変えない。

## 機械で見ること

`npm run diagnosis-shell:selftest`

アプリと拡張の描画に勧誘が無いこと、Web では結果が案内より前にあること、欠けた補完は出ないこと、LP の既存価格が残っていることを見る。
