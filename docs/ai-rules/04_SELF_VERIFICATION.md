# 04 自己検証できる製品を作る(計器の思想)

> 出典: `tsuioku-no-kirameki.com`(ニコ生視聴Chrome拡張)で2026年6〜7月に確立・実証。
> 外部の同型知見:「AIにゲームを自動プレイさせる機能を入れるべき。検証に人間が必要になると開発が一気に遅くなる」(2026-07 のFableゲーム開発知見ポスト)。同じ原理をアプリ一般に適用したのがこの文書。

## 一言でいうと

**AIが人間に「見てきて」と頼まなくても製品の挙動を検証できるよう、製品自身に計器(自己申告)を埋め込む。**
これがあるとバグ調査・調整・回帰確認のループから人間が外れ、開発速度が桁で変わる(実測: 診断1往復が「ユーザーに目視依頼→説明待ち」から「コマンド1回・数秒」になった)。

## 5つのパターン(優先順)

### 1. 計器(instrument)— 製品が自分の挙動を数字で自己申告する
- イベントの**全数**を段階ごとに数える: `検知N → 処理N → 出力N`。段差がそのまま「どこで死んだか」になる。
- **遅延は実測ms**で持つ(直近値+EMA平均。窓バッファ不要でメモリ有界): `体感遅延2.7秒(平均3.5秒)`。
- 出力は1行のテキストに整形して診断画面/ログに出す。**AIがコピペ1枚で切り分けられる形**が正義。

### 2. 嘘をつかない診断
- 「試みた」でなく「実際に起きた」だけを数える(戻り値を見て 'played' のときだけ+1)。
- 失敗は**理由の内訳つき**で数える(`スキップ CD:30 / 上限:0 / 未割当:1`)。内訳ゼロの失敗が出たら「呼び出し自体が起きていない」と機械的に確定できる。
- ✅表示でも件数が食い違うなら必ず1行で明示する。緑のまま黙って壊れる計器は無いほうがマシ。
- **fail-soft設計との衝突に注意**: 取得失敗時に前回値を保全する(データを守る)設計は正しいが、診断側が
  「値が古い/変わっていない」ことだけを見て取りこぼしと誤診断しやすい(2026-07 tsuioku-no-kirameki.com実例:
  「配信終了後にAPIが正常に0件を返すようになった」を「鏡データの取りこぼし」と誤って🔴判定した)。
  解消策は**値そのものでなく出所(provenance)のメタデータを見る**: 書き込み時に
  `{value, prov:{source:'live'|'kept', at, phase}}` のような軽量メタ(数十バイト・既存ペイロードに
  フィールド追加のみ・新storageキーは作らない)を刻み、診断はメタを判定材料にする
  (`kept`=意図的保全→⚪注記、`live`かつ不一致のみ🔴)。fail-softで守るのはデータ、fail-closedで
  判定するのは診断——**両者を繋ぐのがprovenance**、という役割分担が肝。

### 3. 決定論+依存注入(AIが再現テストできるコード)
- 乱数・現在時刻・I/O は関数の引数(deps)で注入する。純関数部分を分離し、テストが「同じ入力→同じ結果」で挙動を固定する。
- これは品質のためだけでなく、**AIが人間なしで検証を回すための前提条件**(再現できないものは検証できない)。

### 4. リモート読取(status:live 型)— 画面を見ずに計器を読む経路
- 診断画面の内容を API/エンドポイント/ファイルに定期 publish し、CLI 1コマンドで取得できるようにする
  (`npm run status:live` 相当)。UIが固まっていても取得できる別経路にしておくのが要点。
- これで「実機で今どうなってる?」がAIの自問自答になる。書き込みは変化があった時だけ(dirty check)・
  読み取りは1バッチにまとめる(計器自身が製品を重くしたら本末転倒。実事故: 計器の読み過ぎで診断が817秒→治療後5ms)。

### 5. 工程ガード — 「ローカルで緑」と「出荷物が健全」は別物
- **check-tracked-imports**(同梱: `templates/scripts/check-tracked-imports.mjs`・無改変で使える):
  git 追跡ファイルだけで import が解決するか検査= git clone 直後(CI/Vercel/ストアビルド)の実体を再現。
  「新規ファイルの add 忘れ」はローカル検証(作業ツリー基準)では原理的に検出できない。CI と pre-push の build 直後に置く。
- **汎用診断キット**(同梱: `templates/diagnostics/`・`node diagnostics/run.mjs <対象ディレクトリ>`):
  上記の check-tracked-imports に加え lockfile不一致・秘密情報の追跡漏れ・巨大ファイル追跡の3本を束ね、
  依存ゼロでこのキット外の任意のJS/TSリポにもそのまま使える形に一般化したもの。詳細は `templates/diagnostics/README.md`。
- **バージョン混在の実行時検知**: ビルド時にバンドルへ版番号を焼き込み、起動時にランタイムの版と比較。
  不一致なら「更新が中途半端です。リロードしてください」バナー。黙って壊れる→見えて直せる、に変える。
- リリース3点(バージョン・changelog・成果物)の同期は機械チェックにする(verify:bump 相当)。

### 6. メタ診断 — 診断計器自体の網羅性を機械的に保証する
- 診断計器が増えるほど「セルを足したのにレジストリ/集計に登録し忘れて黙って対象外になる」事故が起きる
  (2026-07 tsuioku-no-kirameki.com実例: 診断セル追加とレジストリ登録が別コミットになり、片方が漏れて
  そのセルが完全性スコアの対象外のまま気づかれなかった)。
- 解消策は**fixtureに依存しない静的ソーススキャン契約テスト**: 診断UIのソースファイルをテストが
  `readFileSync`して、セルidをリテラルとして正規表現抽出し、レジストリ側の登録一覧と集合等値を断言する。
  fixtureベースのテスト(特定の状態を再現してセルが出るか確認する形)は「そもそもそのセルを発生させる
  fixtureを書き忘れる」と穴が残るため、**ソースを直接読む静的スキャンの方が網羅性を取りこぼさない**。
- ランタイム変更ゼロ・実行コストはテスト実行時のみ。「一次集計を増やす」ことよりも安く効果が高いので、
  診断強化に着手するときはまずこれから入れる(他の計器強化の土台にもなる=登録漏れが物理的に不可能になる)。

## プラットフォーム別の適用メモ

| プラットフォーム | 計器の置き場 | リモート読取 |
|---|---|---|
| Web(Next.js/Vercel) | 開発者向け /debug ページ or console構造化ログ | API route に publish→CLI で GET |
| Chrome拡張 | 診断ページ(status.html 型) | Serverless(api/status 型)へ publish |
| iOS/Android(Capacitor/TWA) | server.url 連動型なら Web と同一計器がそのまま動く | 同上(Web側に集約) |

## アンチパターン(実事故由来)

- 計器のためにデータ本体(Blob等)を読む → 件数だけなら count() 系で。**計器は軽くなければ計器でない**。
- タイムアウトで表面だけ次に進む(Promise.race)→ 裏で操作が生き続けて多重競合。in-flight ガード(前回未解決中は再発行しない)を併用する。
- 検証に人間の目視・操作を組み込む → 「反映して」「押してみて」の往復が積もると開発が止まる。人間に残してよいのは(a)最終リロード等の権限操作 (b)音・体感など機械化不能な官能評価、の2つだけ。
