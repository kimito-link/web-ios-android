# 01_CORE_RULES

## 1. 適用範囲

- 人間開発者と AI 実装エージェントの両方に適用する
- Web 実装では本ドキュメントを最優先の共通基準とする

## 2. 設計と実装の原則

- 仕様の曖昧さを放置せず、実装前に要件を明文化する
- **同機能の重複実装をしない（既存部品を検索して再利用）**
  > ⚠️ このルールは「実装前」に必ず読むこと。文章として存在するだけでは効かない
  > （2026-08-31実損: 姉妹プロジェクトに既にある「人物（アイコン・ID・名前）」の共通表現を
  > 確認せず劣化版を新規実装した。詳細: `../../_docs/REPLY-to-tsuioku-ai-maze-pattern-2026-08-31.md`）。
  > 実装前に必ず `node ../../ai-hub/bin/hub.mjs find --tag <関連タグ>` を実行して確認する。
- 変わる部分のみコンポーネント化し、固定骨格は過剰抽象化しない
- **ヘッダー・フッター等、複数ページ/複数プロジェクトで繰り返し使う部品は1箇所で定義する**
  （2026-09-01確立）。プロジェクト内の重複だけでなく、**プロジェクトをまたいだ重複**も対象。
  > ⚠️ 実損: web-ios-androidキット自身の`site/`には共通ヘッダー・フッターの実装
  > （`site/scripts/site-chrome.js`、JS実行時注入方式）が既にあったが、`templates/`へ
  > 一般化されていなかったため、別プロジェクト（line-bot/apps/lp配下）が新規に複数ページの
  > サイトを作る際、この実装の存在に気づけず、ページごとにheader/footerを個別実装した。
  > 複数ページの静的サイトを新規に作るときは、まず
  > [`templates/web/site-chrome/`](../../templates/web/site-chrome/README.md) を使う
  > （ビルドツールを使うプロジェクトは対象外。フレームワーク標準の共通レイアウト機構を使う）。
- 1 変更 1 意図を基本に、小さくコミットする

## 3. UI/UX 原則（レスポンシブ必須）

- モバイル・タブレット・デスクトップで表示崩れがないこと
- タップ領域、文字サイズ、余白をデバイス別に最適化する
- 主要操作は折り返しやオーバーフローで失われないこと

## 4. URL / SEO / 配信ルール（固定）

- URL はディレクトリ形式（例: `/price/`）を使用する
- `index.html` を URL に含めない
- `www` あり/なしを統一（推奨: 非 `www`）
- `http` から `https` へ恒久リダイレクト（301）
- canonical は正規URLに統一する

## 5. セキュリティ原則

- トークンやシークレットをソース・ログ・プロンプトに出力しない
- 環境変数の中身を確認したいときも `grep`/`cat` で値そのものを出力しない。存在確認だけに留める
  （例: `${VAR:+yes}` 形式）。新しい値を受け取ったら、それ以降のログ・コマンド出力に生の値を
  極力残さない（Cloudflare/Vercel/GitHub/Stripe等どの認証トークンにも共通。実例は
  [`_docs/cloudflare-workers-token-expiry-knowledge-base.md`](../../_docs/cloudflare-workers-token-expiry-knowledge-base.md)参照）
- 入力値検証、XSS/SQLi/CSRF 対策を実装前提にする
- 本番デバッグコードや不要ログを残さない

### 5-1. 公開前の最低4問（全プロジェクト共通の指針・2026-10-14採用）

アプリ・API・拡張・LPを**公開する前に**、AIが自分で次の4つを実コードに当てて確認し、結果を報告する。
非エンジニアの個人開発者が「AIに頼むから」と公開するケースで、最も事故になりやすい4点
（出典: X投稿 2026-10-13「非エンジニアの個人開発者は聞け」。内容はこのキットの言葉に言い換えた）。
**「たぶん大丈夫」で通さない。ファイルと実行結果を根拠に答える。**

| # | 問い | 確認のしかた（実測） | 機械検査 |
|---|---|---|---|
| 1 | AIのAPIキーなど**秘密がアプリ内（ブラウザに届くコード・アプリ本体・公開リポ）に埋め込まれていないか** | ビルド成果物(dist等)・git追跡ファイル・公開JSを検索。秘密を要る処理は**サーバー側**に置く | ✅ `templates/scripts/verify-no-secrets-in-dist.mjs`（焼き込み検出）。追跡漏れは `templates/diagnostics/check-secrets-not-tracked.mjs` |
| 2 | **認証・認可をサーバー/DB側で行っているか**（画面側の出し分けだけに頼っていないか） | 画面を隠しているだけのボタン・管理画面を、**ログインなし／別ユーザーで直接APIに叩いて**拒否されるか確認 | ❌ 意味判断が要る（下記） |
| 3 | **他人のデータを閲覧・変更・削除できる穴がないか** | 自分のアカウントで他人のID・URL・レコードを指定して読み書きし、拒否されるか確認（DBの行単位ルール・所有者チェックの有無も読む） | ❌ 意味判断が要る（下記） |
| 4 | **大量リクエスト・不正利用で高額請求が出る作りになっていないか** | 課金されるAPI（LLM・SMS・メール・ストレージ等）の前に、**認証＋レート制限＋プロバイダ側の月額上限**があるか。未ログインで叩けるか | ❌ 意味判断が要る（下記） |

★機械化できない理由（「新しいルールを書いたら機械検査化を検討する」節の手順3）: ②③④は「その処理が
誰に許されるべきか」「どの呼び出しが課金されるか」という**仕様の意味**に依存し、コードの静的検査だけでは
「あるべき拒否」を定義できない。**検出できる客観的事実（❶の焼き込み）だけを機械化**し、残りは
**公開前にAIが実リクエストで確かめて報告する**運用にする。`verify-security-score.mjs` の満点は
「ヘッダ等の兆候が無い」ことしか意味せず、②③④の安全を保証しない（過信しない）。

#### 5-1a. 4問の第一の実行手段: Claude Security（公式プラグイン・2026-10-16採用）

②③（認可の穴・他人データの穴）は「コードを読んで筋が通る」では足りず、実際に攻撃経路を組み立てて
確かめる必要がある。**車輪の再発明をしない**（CLAUDE.md 基準②）ので、Anthropic 公式の **Claude Security**
プラグイン（`anthropics/claude-plugins-official` の `plugins/claude-security`、v0.12.0 で実物を確認）を
**第一の手段**にする。アーキテクチャの把握 → 脅威モデル → 全コンポーネントの探索 → 各指摘を独立した検証役が
反証しようとして残ったものだけを報告、まで Claude Code のセッション内で行い、パッチ案も作る
（**適用はしない**。適用・コミット・pushは別の依頼として自分が行う）。

| 項目 | 内容 |
|---|---|
| 導入 | `/plugin install claude-security@claude-plugins-official` → `/reload-plugins`（マーケットが無ければ先に `/plugin marketplace add anthropics/claude-plugins-official`） |
| 実行 | `/claude-security`（メニュー）。「全体」「今のブランチの差分」「PRの差分」「1コミット」を選べる。例: `/claude-security scan my branch at high` |
| 推奨モデル | Claude Opus 5.5 または Fable 5.1（`/model` で選ぶ）。一部が Opus 4.8 に切り替わることがある |
| 結果 | リポ内の `CLAUDE-SECURITY-<時刻>/` に、`RESULTS.md`（人が読む）・`.jsonl`・`.sarif`・刻印 `CLAUDE-SECURITY-REVISION-<sha12>[-dirty].json`。★自前の `.gitignore` を持つのでコミットされない |
| 必要なもの | Python 3.9 以上（PATH）／差分・パッチは git の作業ツリー |
| 費用 | 実行のたびに「時間とトークンの見積り」の確認が出る。**公開前と大きな変更の後に絞る**（毎コミットで回さない） |
| 料金・プラン | **プラグイン自体に別料金は無く、通常の Claude Code の利用枠（トークン）を消費する**。前提は「有料プラン・Anthropic API・外部プロバイダ(Bedrock 等)のいずれか」（Pro は `/config` で Dynamic workflows の有効化が要る）。5時間枠・週間上限を他の作業と共有するので、**枠が逼迫しているときは小さい範囲（今のブランチの差分・medium）から**。★ホスト型の「Claude Security」アプリ（Claude.ai 上）は別物で Enterprise 向けの公開ベータ。ホスト型のモデル(Mythos)はプラグインでは使えない |

- **どこで走らせるか**: 自分のコードに対して。**信頼できないリポジトリ（外部の依存・見知らぬリポ）は
  sandbox-runtime の中で**（公式の推奨。プラグインは独自の隔離を足さず、そのセッションの権限で動く）。
- **過信しない**（公式 README も明記）: スキャンは**非決定的**で、同じコードでも指摘が変わる。「0件」は安全の証明では
  ない。SAST・依存の脆弱性検査・コードレビューの**代わりではなく補完**。結果ファイルは、秘密値を `[REDACTED]` に
  置き換える処理を通るが**モデルの最善努力**なので、共有する前に目で確かめる。
- **機械検査（走らせたかどうか）**: `templates/scripts/check-security-scan-ran.mjs`。刻印から「**いまの HEAD に対する
  スキャンがあるか**」「**CRITICAL / HIGH が残っていないか**」を読む。**走らせていない／HEADより古いは赤にせず exit 2
  （測れていない）**で鳴らし続ける（赤にすると通すためだけに形だけ走らせる動機を作る＝改善台帳の規約③と同じ）。
  CRITICAL / HIGH が残っていれば exit 1。★指摘の中身・網羅性の妥当さは機械では見ない（意味判断）。
  `run.mjs` には配線しない（スキャンが未導入のリポで診断全体が exit 2 になり CI を壊すため。公開前に呼ぶ）。
- テレメトリ: 利用回数などが Claude Code の仕組みで送られる。止めるなら `DISABLE_TELEMETRY=1`（公式の記述）。
- **ライセンス**: プラグインは Anthropic の独占的なソフトウェア（LICENSE を実読）。**自分の社内利用で Claude Code とともに使うのは可。再配布・他社製品との併用は不可**。このキットは**導入手順を案内するだけ**で、プラグインを同梱・配布しない。
- 料金・プランの根拠: 公式 docs（`https://code.claude.com/docs/en/claude-security`）と製品ページの記述（2026-10-16 に確認。料金表の末尾など一部は未確認）。プランや上限は変わりうるので、**迷ったら実行前の見積りの表示と公式 docs を正とする**。

### 5-2. コードコメントの書き方（全プロジェクト共通の指針・2026-10-16採用）

AIは別セッションに引き継がれるたび、前の文脈なしにコードを読み直す。人間も、作者がいなくなった後に
読む。そこで「何をしているか」ではなく「**なぜそうなっているか**」を、決まった場所に残す。

| 場所 | 書くこと | 必須か |
|---|---|---|
| **ファイル先頭** | 役割・使い方・（あれば）終了コードなどの約束事・**なぜ要るか**（きっかけの実損） | **新規ファイルは必須**（機械検査あり） |
| **責務のまとまり（関数・ブロック）** | 順序の理由・罠・触ると壊れる点・採らなかった案の理由 | 非自明なものだけ |
| **1行ごと** | ——書かない。コードを読めば分かり、直すと嘘になって腐る | 不要 |

- 先頭コメントは、記号と空白を除いて**20文字以上**の本文があること（`// x` や罫線だけは不可）。
- **機械検査があるのは「先頭コメントの有無」だけ**: `templates/diagnostics/check-file-header-comment.mjs`
  （`run.mjs` 経由。**新しく追加したファイルだけ**を赤にする。テスト・型定義・生成物・設定は対象外）。
- ★機械化できない理由（「新しいルールを書いたら機械検査化を検討する」節の手順3）: **コメントの中身が
  正しいか・十分か**は意味判断が要る。ここは人間とAIのレビューに残す。
- 既存ファイルの一括修正はしない（機械的に埋めるとコメントの質が落ちる）。**触るときに足す**。
- 直したらコメントも直す。コードと食い違ったコメントは、無いより悪い。

### 5-3. ストア審査の追加リスク: 隠し機能とクリエイティブアセット（全プロジェクト共通の指針・2026-10-18採用）

2026-10-16、Apple が App Review Guidelines を改訂した（公式: https://developer.apple.com/news/ ・本文を実読して確認済み）。
同じ告知で、Apple は昨年**19.3万件超の開発者アカウントを不正・悪用で終了**したと述べている。
「今日通ったから明日も安全」ではなく、**提出する版が、審査に見せた通りであり続けること**が問われる。

| 改訂 | 内容（要点） | このキットでの扱い |
|---|---|---|
| **2.5.19**（新設・旧2.3.1から独立） | 隠し・休眠・未申告の機能を入れない。審査後に機能を足すのは削除と**開発者アカウント終了**の対象。難読化で隠すのも同じ | CHECK 31（難読化・取得文字列の実行の兆候を warn）。全機能を審査メモに書く運用（下記） |
| **2.3.14**（新設） | クリエイティブアセット（商品ページのヘッダー・検索結果に出せる画像/動画）。アプリの中身・ブランドに関係し、全年齢向けで、**他アプリへの誤解を招く言及・検証できない主張・特定/割引の価格を入れない** | CHECK 32（文言の価格=fail・No.1等の主張=warn・画像は目視を促す warn。ヘッダー 3840x1646 / 検索結果 3:2 の寸法・形式・透明度は fail、素材が無ければ warn）。★上げられるのは版が編集できる間だけ。手順と仕様は [`_docs/creative-assets-header-search.md`](../../_docs/creative-assets-header-search.md) |
| 1.2 | UGC アプリの審査対象を明確化。AI生成を含む**同意のない性的画像**を事前に防ぎ・削除する義務。怠ると Developer Code of Conduct 違反 | 該当アプリのみ。通報・ブロック・フィルタの実装を公開前4問と同じ強度で確認 |
| 3.1.1(a) | 音楽ストリーミングの項を StoreKit 外部購入リンクの項に統合。リンクは許可された行き先なら可 | 既存 CHECK 18（アプリ外購入への導線）の対象。行き先が許可されたものか確認 |
| 5 | 人身取引・児童搾取に関わるアプリは削除され、**代替配信でも遮断** | 該当しない（念のため記録） |

**server.url 型（Capacitor で本番Webをそのまま表示する）のアプリは、この規則の影響が大きい。** 画面の中身はサーバー側で
いつでも変えられるので、「審査後に機能が増えた」状態に**構造的になりやすい**。守ること:
1. 審査メモ（App Review notes）に、**サーバー配信で機能が決まる作りであること**と、**その時点の全機能**を書く。
2. 審査後に**新しい機能の種類**（決済・UGC・AI生成・外部リンク・年齢制限に関わる内容）をサーバー側だけで足さない。足すなら新しい版として提出し、審査メモも更新する。
3. 機能を隠すために難読化・バンドル分割・フラグでの出し分けをしない（休眠機能は残さず消す）。実験用のフラグを使うなら、審査メモに書く。

**クリエイティブアセットの作り方**: アプリを正しく表すものだけ。値段・「今だけ○%OFF」・「No.1」・競合名は入れない。
画像の中の文字は機械では読めない（CHECK 32 は文言ファイルしか見ない）ので、**画像は目視で**確認する。

**アカウント終了の実数（公式・2025年）**: 終了 193,035 件のうち 99.8% が DPLA 3.2(f)「不正」分類で、復元は 499 件。終了されると**アカウント内の全アプリが止まる**ので、「不正と見なされる形を作らない」を最優先にする（読み方・守り・未確認は [`_docs/apple-account-termination-risk.md`](../../_docs/apple-account-termination-risk.md)）。

★機械化の範囲と限界（「新しいルールを書いたら機械検査化を検討する」節の手順3）: 「審査メモに全機能が書いてあるか」
「バナーの主張が事実か」は意味判断で、機械では決められない。**形で検出できるもの**（難読化の識別子・取得文字列の実行・
価格表記）だけを CHECK 31・32 にした。緑は「兆候が無い」だけを意味し、「審査に通る」を保証しない。
詳細・出典は [`_docs/apple-reject-knowledge-base.md`](../../_docs/apple-reject-knowledge-base.md)「2026-10-16 改訂」節。

## 6. AI 実装時の必須行動

- 実装前に `AI_INSTRUCTIONS.md` を必ず読む
- 変更理由を簡潔に説明し、根拠のない推測実装を避ける
- 実装後はテスト結果と未解決課題を明示する

## 7. 禁止事項

- 既存と同等機能の新規コンポーネント乱立
- `!important` 依存でのスタイル上書き常態化
- 「とりあえず動く」だけの未検証コミット
