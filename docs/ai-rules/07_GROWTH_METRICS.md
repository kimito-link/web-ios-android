# 07_GROWTH_METRICS — 事業の数字を最大化する物差し（CVR・LTV・CPA ほか）

> **今の到達点: 採用（2026-10-22）。CLAUDE.md「設計方針」の1本目の軸（旧「CVR/LTV最大化」）の正本。**
> 役割: AI が「どちらの案にするか」を自分で決めるときの、事業の数字の物差しを1か所に置く。
> 使い方: 判断が割れたら §4 の順に当てる。新しい機能・LP・アプリを企画するときは §2 の表で「どの数字をどちらへ動かすか」を1行書いてから作る。
> なぜ要るか: これまでの軸は CVR と LTV の2つだけで、**お客を連れてくる費用（CPA）**と、紹介・継続・評価のような「放っておいても増える力」が物差しに入っていなかった。本人指示（2026-10-22）「全体の設計を CVR・LTV・CPA 最大化で。ほかにも最大化できる概念があるので全部入れて」。
> 関連: [CLAUDE.md「設計方針」節](../../CLAUDE.md)（3軸の定義）／[CLAUDE.md「有料APIを使う機能は『使われるほど黒字』」節](../../CLAUDE.md)（原価の守り。粗利の正本はそちら）／[06_ENGINEERING_CHECKLIST.md](06_ENGINEERING_CHECKLIST.md)（外から見えない品質の点検表）。

## 0. 「CPA最大化」の読み方（先に決めておく）

CPA は「お客さん1人を連れてくるのにかかった費用」。**数字が小さいほど良い**。だから本人の言う「CPA最大化」は
**CPA の効率を最大化する＝同じお金でより多くの人に来てもらう＝CPA を下げる**、と読む。
広告費をゼロにしても、紹介・検索・ストア検索で来る人が増えれば CPA は下がる。「広告を止める」だけが CPA 改善ではない。

## 1. 北極星（全部の数字を1つにまとめる式）

数字がたくさんあると、どれを優先するかでまた迷う。だから**最後は1つの式に戻す**:

```
北極星 = LTV ÷ CPA   （1人のお客さんが生涯で残す粗利 ÷ その1人を連れてくる費用）
  LTV  = ARPU（1人あたりの月の売上）× 粗利率 × 続く月数（≒ 1 ÷ 月の解約率）
  補助 = 回収期間（CPA を何か月で取り戻せるか ＝ CPA ÷（ARPU × 粗利率））
```

- 目安は **LTV÷CPA が 3 以上、回収期間 12 か月以内**（サブスク事業でよく使われる経験則。このキットの実測ではない。実測が出たら置き換える）。
- 無料アプリ・無料ツールでも同じ式で考える。売上の代わりに「続けて使う人の数」「紹介で来る人の数」「本業への送客」を価値として数える。
- この式を見ると、上げられる「つまみ」は5つしかない: **①来る人を安く増やす（CPA↓）②有料・登録になる率（CVR↑）③1人の単価（ARPU・客単価↑）④続く期間（継続率↑・解約率↓）⑤原価を下げる（粗利率↑）**。§2 の表はこの5つを細かくしたもの。

## 2. 最大化する数字の一覧（お客さんの流れの順）

| 段階 | 数字 | やさしい意味 | 向き | よく効く打ち手（例） |
|---|---|---|---|---|
| 来てもらう | **CPA**（獲得単価） | 1人を連れてくる費用 | ↓ | 自然流入・紹介を増やす、広告は ROAS で選ぶ |
| 来てもらう | **ROAS**（広告の回収率） | 広告1円が何円の売上になったか | ↑ | 回収が悪い広告は止める |
| 来てもらう | **自然流入の割合** | 広告なしで来た人の割合（検索・SNS・ストア検索） | ↑ | SEO・発信ルーティン（[DISTRIBUTION-ROUTINE](../DISTRIBUTION-ROUTINE.md)） |
| 来てもらう | **バイラル係数（K）** | 1人が何人を連れてきてくれるか | ↑ | 結果を人に見せたくなる共有機能・招待 |
| 来てもらう | **ストアの転換率** | ストアのページを見た人のうちインストールした割合 | ↑ | スクリーンショット・プレビュー動画・アイコン・説明文（ASO） |
| 使い始める | **アクティベーション率** | 入れた人のうち「これは良い」と感じる最初の体験まで届いた割合 | ↑ | 初回の手順を減らす、ログイン前に価値を見せる |
| 使い始める | **価値までの時間（TTV）** | 最初の「良い」までにかかる時間 | ↓ | 待ち時間・入力項目を削る |
| 決める | **CVR**（転換率） | 見た人のうち登録・購入した割合 | ↑ | 伝わる言葉・迷わない導線（CLAUDE.md「売り方の品質」） |
| 払う | **ARPU / ARPPU** | 全員／払った人の1人あたり売上 | ↑ | プラン設計・上位プラン・追加パック |
| 払う | **客単価（AOV）** | 1回の購入の金額 | ↑ | まとめ買い・セット |
| 払う | **粗利率** | 売上から原価（AI の API 代など）を引いて残る割合 | ↑ | キャッシュ・予算の守り（CLAUDE.md「使われるほど黒字」節） |
| 続ける | **継続率（D1/D7/D30）** | 1日後・7日後・30日後もまだ使っている割合 | ↑ | 通知・LINE・習慣になる仕組み |
| 続ける | **解約率** | 1か月でやめる人の割合 | ↓ | 解約理由を聞いて直す、引き止めの提案（[apple-retention-messaging-api](../../_docs/apple-retention-messaging-api.md)） |
| 続ける | **NRR**（既存客の売上維持率） | 去年のお客さんだけで、今年の売上が何%残ったか | ↑ | 使うほど価値が増える作り |
| 勧める | **NPS** | 「人に勧めたいか」0〜10点の答えから出す点数 | ↑ | 一番の不満を直す |
| 勧める | **ストア評価（★）・レビュー数** | ストアでの平均点と件数 | ↑ | 良い体験の直後に公式の仕組みで評価を頼む（§3） |
| キット固有 | **公開到達率** | キットを使い始めた人のうち、実際にストア・Web へ公開まで届いた割合 | ↑ | 詰まる所を自動化（[FIRST-SUBMISSION-blockers](../../_docs/FIRST-SUBMISSION-blockers.md)） |

全部を毎回測る必要はない。**その変更が動かす数字を1〜2個だけ選んで**、「どれを・どちらへ」を書いてから作る。

## 3. 上げるために壊してはいけないもの（ガードレール）

数字だけを追うと、人をだまして数字を作る方向へ流れる（数字を目的にすると数字が意味を失う＝グッドハートの法則）。
これは「100年メンテナンスのいらない設計」とぶつかる——信用を削って作った数字は、後で評価・返金・規約違反として必ず返ってくる。だから次は**最初に捨てる案**:

- **解約しにくくして LTV を上げる**（解約の入口を隠す・手順を増やす）。各ストアの規約・特定商取引法の表示の決まりに触れ、★評価と信用を失う。
- **★5を付けそうな人だけに評価を頼む**（評価の選り分け）や、評価と引き換えに特典を出すこと。評価の依頼は iOS の `SKStoreReviewController`／Android の In-App Review API という**公式の仕組みだけ**を使う。
- **誤解させる言葉で CVR を上げる**（無料と見せて実は有料、根拠の無い数字）。数字・実績は出典つき（CLAUDE.md 基準③、`npm run claims:provenance`）。
- **原価を見ずに無料枠を広げて獲得を増やす**（使われるほど赤字になる）。CLAUDE.md「使われるほど黒字」節の式を先に書く。
- **プライバシー・セキュリティを削って速くする**（[01_CORE_RULES §5-1](01_CORE_RULES.md) の公開前4問）。

ガードレールとして見る数字: 返金率・苦情や問い合わせの件数・ストアの却下数・★評価・解約理由。これらが悪化する案は、他の数字が良くても採らない。

## 4. AI が判断するときの順番（選択肢を出して止まらないための物差し）

判断が割れたら、人に聞かずにこの順で当てて**自分で1つに決めて実行し、決めた理由を報告する**（CLAUDE.md「選択肢を出して止まらない」節）:

1. **ガードレール（§3）を割る案は捨てる。**
2. **LTV÷CPA がより上がる方**を選ぶ（§2 のどの数字が動くかで考える）。
3. 同じくらいなら、**回収が早い方・すぐ効果が測れる方**。
4. まだ同じなら、**保守の手間が少ない方**（保守の手間も原価＝100年メンテナンスのいらない設計）。
5. 新しいアプリ・事業の柱の企画なら、最後に**商品インパクトの5問**で、より野心的な方へ倒す。

★これらの数字・この順番は**自分が決めるための物差し**であって、人に選ばせる選択肢ではない。「CVR重視にしますか、LTV重視にしますか」「CPAを優先しますか」のように**物差しそのものを質問に出さない**（`.claude/hooks/check-ask-preceded-by-research.mjs` が質問文に CPA・LTV・ROAS などが入っていると警告する）。

## 5. 正直に測る（測れていない数字を良いと言わない）

- 数字は3つの状態で書く: **良い／悪い／まだ測れていない**。測れていないものを「たぶん良い」にしない（このキットの計器の考え方と同じ。[04_SELF_VERIFICATION](04_SELF_VERIFICATION.md)）。
- 見込みの数字と実際の数字を混ぜない。見込みには「見込み」と書く。
- 測る場所の例: Web は Vercel Analytics 等のアクセス解析、iOS は App Store Connect の分析、Android は Play Console の統計、課金はストアの売上レポート。新しく計測の仕組みを作る前に、これらで足りないかを先に見る（車輪の再発明をしない）。

## 6. 機械検査（どこまで機械で見られるか）

- **見ている**: 物差しの名前（CVR・LTV・CPA・ROAS・ARPU・NPS など）が AskUserQuestion の質問文・選択肢に入っていないか（`.claude/hooks/check-ask-preceded-by-research.mjs` の `DESIGN_PRINCIPLE_KEYWORDS`。非ブロッキングの警告。タグ無しの質問そのものは別の検査で拒否される）。
- **見ていない（理由）**: 「その案で本当に LTV÷CPA が上がるか」は、作る前には測れず、作った後の実測でしか分からない意味判断なので、事前の機械検査にはしない。企画書に「動かす数字」の1行があるかを検査する案はあるが、新しい検査は実損が出てから足す（CLAUDE.md「新しいルールを書いたら機械検査化を検討する」節の3番）。
