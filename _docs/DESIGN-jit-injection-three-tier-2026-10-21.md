# 設計: 指示書の三層注入（常時核 / 着手直前のJIT / 検索任せ）— 2026-10-21

> **今の到達点: 設計のみ・実装未着手（意図的に実装しない。理由は §5）。**
> 親: [`DESIGN-overall-design-council-2026-10-21.md`](DESIGN-overall-design-council-2026-10-21.md) §7 P10（コンテキスト工学）。
> 前提: P0(ratchet budget hook) 配線済み・P1 で核を 370 行まで減量済み。この設計は「核が痩せた後」に書く約束だった
> （先に書くと「注入があるから核に足してよい」の口実になるため・council の順序原則）。

## 1. 用語（初出の言い換え）

- **核（コア）**: `CLAUDE.md` の冒頭から `<!-- core:end -->` マーカーまで（約370行・上限450）。セッション開始時に必ず読み込まれる必読部分。
- **JIT注入（Just-In-Time injection）**: 「その作業に入る直前に、必要な節だけを目の前に出す」こと。常時は出さない。
- **三層**: 指示書を「いつ・どれだけ届けるか」で3段に分ける考え方。下の §2。

## 2. 三層（何を・いつ・どれだけ）

| 層 | 中身 | いつ届くか | 量 | 守りの機構 |
|---|---|---|---|---|
| **第1層: 常時核** | `CLAUDE.md` の核（非交渉ルール・4基準・5類型・★質問前の4手順・知見の地図） | セッション開始時に自動（`@web-ios-android/CLAUDE.md` import） | 小さく固定（≤450行） | `check-claude-md-budget-ratchet.mjs`(P0) が「増やす編集」を deny。`require-claude-md-read.mjs` が核の既読を Edit/Write 前に強制 |
| **第2層: 着手直前のJIT** | その作業に固有の節・HOWTO（例: site/ を触る→LP-SYNC.md、会議→COUNCIL-HOWTO.md、ストア提出→store-guard、IAP→既存プロジェクトの型） | その種類の作業に入る直前 | 必要な1節だけ | 下の §3（**ポインタ注入**＝ファイル名を出すに留め、本文は注入しない） |
| **第3層: 検索任せ** | 上記以外すべて（却下KB・実損KB・各HOWTO・ai-hub 横断資産） | 必要になったとき自分で探す | オンデマンド | 核の「知見の地図」表＋`Grep`/`Glob`/`node ../ai-hub/bin/hub.mjs find` が入口 |

**原則**: 第1層は「全員・毎回」。第2層は「その作業の人・そのときだけ」。第3層は「探せば出る」。核が小さいほど毎回のコストが下がり、decay（重要ルールが中盤に埋没して守られない）を防げる。

## 3. 第2層（JIT）の実装方式の候補（実装は未着手）

**方式A: ポインタ注入 hook（PreToolUse 非ブロッキング）**
- 作業の種類を道具の引数から推定し（例: `Edit site/**` → LP系、`Bash` に `council`/`dispatch` → 会議系）、該当 HOWTO の**ファイルパスを1行**で `additionalContext`/`systemMessage` に出す。
- ★**本文は注入しない**（出すのはパスだけ）。理由: 本文注入は毎回のトークンを食い、第1層肥大と同じ病になる。読むかどうかは受け手が決める（Read すれば最新が手に入る）。
- 既存の `check-target-file-reachability.mjs`・`check-write-preceded-by-search.mjs` と同じ transcript 走査・非ブロッキング・fail-open 型で作れる（新基盤は増やさない）。

**方式B: skill 経由**
- 作業の種類に対応する skill（例: store-guard・council-fable）が、その節を読む手順を内包する。Claude Code の skill 一覧から選ばれたときに該当文脈が載る。
- A より「作業の明示的な開始」に紐づく（道具の引数推定より誤爆が少ない）。既に `self-verification` 等の skill がこの形。

**推奨の方向**: まず**方式A のポインタ注入**を1種類（最も誤解の多い「site/ を触る前に LP-SYNC.md」）だけ試作し、偽陽性/有用性を見てから広げる。A と B は排他でなく、明示開始があるものは B、暗黙に始まるものは A で補う。

## 4. 不変条件（この設計が守らせること）

1. **第2層の存在を、第1層を太らせる口実にしない**。注入があっても核の予算（P0 ratchet）は動かさない。新しい実損ルールは「核に規範1行＋EVIDENCE、本文は `_docs/`/`site/learnings/`」（P1 の relocation 方式）を続ける。
2. **注入は本文でなくポインタ**（ファイル名）。量の管理を機械（ratchet）が効かせられる第1層に集約し、第2層は量を持たない。
3. **fail-open**。JIT が出なくても作業は止めない（第3層の検索で辿れる）。JIT はあくまで「気づきの前出し」。
4. **正本は散らさない**。第2層が指すのは既存の HOWTO/KB の実ファイル。注入のためにコピーを作らない。

## 5. なぜ今は実装しないか（意図的な据え置き）

- P10 は council で「方向採用だが P1 で核が痩せた後に**設計**」とされた項目。**実装までは射程外**。先に注入機構を作ると「どうせ注入されるから核に足してよい」という逆インセンティブが働き、P0/P1 で確立した「核を小さく保つ」規律を崩す。
- まず第1層（核）と第3層（検索＋知見の地図）だけで運用し、「この作業の前にこの節を見逃して事故った」という**実損が出た種類**にだけ、方式A のポインタ注入を1件ずつ足す（実損ドリブン・CLAUDE.md「新しいルールを書いたら機械検査化を検討する」と同じ、必要になってから個別対応する流儀）。
- つまりこの文書は「三層という地図」と「第2層を足すときの型（ポインタ注入・不変条件4点）」を**先に決めておく**もので、機構を今建てるものではない。

## 6. 未確認・次にやること（宣言して残す）

- 方式A の作業種別推定の精度（道具引数からの推定はどれだけ誤爆するか）は未計測。試作して transcript で偽陽性率を見るまで本採用しない。
- 第2層を足す最初の1件は「site/ を触る前に `site/LP-SYNC.md`」が最有力（実損の頻度が高い領域）。ただし実損ログが溜まってから着手する。
