# 実行時の真実を計る — 「コードを読んだ推論」で満足しないためのKB

> 得られた実戦: reply-copilot-openrouter-v2（AI返信サジェスト）の返信品質改善、2026-07-30。
> 症状の原因を3回続けて誤特定し、`fetch` をラップした1回の実測で全て解決した。
> 同じ罠は「設定が効かない」「直したのに変わらない」系のあらゆる調査で踏む。

---

## 一言でいうと

**コードを読んで「この経路が使われるはず」と推論した時点で、まだ何も確かめていない。**
実際に何が送信・実行されているかを1回実測するだけで、推論3回分の空振りが消える。

---

## 症状

「直したのに、何も変わらない」。具体的には:

- ソースを修正してデプロイしたのに、出力が1文字も変わらない
- 設定値を変えたのに、挙動が変わらない
- ログには「新しいコードが動いている」ように見えるのに、結果が旧来のまま
- 複数の候補箇所を順番に直したが、どれも効かない

## 原因

読んだファイルが**実際には使われていない**、または**別のものに上書きされている**。
実際に踏んだ3パターン:

| 思い込み | 実際 |
|---|---|
| 「この定数がプロンプトに入っているはず」 | 受け皿のオプションはあるが、渡している呼び出し元が**リポジトリ全体で0件**。UI表示用に返るだけで、生成には未使用だった |
| 「この軽量プロンプトが使われる経路のはず」（機能フラグもONだった） | 実際は別経路（巨大プロンプトのビルダー）が使われていた。フラグはONでもその分岐に到達していなかった |
| 「LLMが汎用文を返している」 | LLMは別の文を返していた。**後処理が固定の定型文に差し替えていた** |

いずれも「コードを読む」だけでは判別できない。**実行時にしか分からない。**

## 直し方

### ① 送信されている中身を丸ごと捕獲する（外部APIを叩くなら最優先）

`globalThis.fetch` をラップして、実際のリクエストボディを見る。Node でも動く。

```js
const realFetch = globalThis.fetch;
let captured = null;
globalThis.fetch = async (url, opts) => {
  if (String(url).includes('api.example.com') && opts?.body) {
    try { captured = JSON.parse(opts.body); } catch {}
  }
  return realFetch(url, opts);
};
// …対象の処理を実行…
console.log('全長:', JSON.stringify(captured).length);
console.log('自分が入れた文言を含むか:', JSON.stringify(captured).includes('目印の文字列') ? 'YES' : 'NO ← 使われていない');
```

**「自分が追加した文言が実際に含まれているか」を目印で検索する**のが要点。
これをやらずに「たぶん入っている」で先へ進むと、使われていないファイルを何度も直す。

実測でこう分かった: プロンプト全長 **16,956文字**、冒頭が指示の羅列で肝心の入力データは末尾。
ファイルを読んで想像していた構造と全く違った。

### ② 「入力」と「最終出力」を並べて、途中で書き換わっていないか見る

外部から返ってきた生の値と、画面に出る直前の値を両方printする。
一致していなければ、その間の後処理が原因。

```
外部APIの生応答:  ...引き続きよろしくお願いいたします。
最終出力:        ...内容を確認のうえ、改めてご連絡いたします。   ← 別物＝後処理が書き換えている
```

これで「LLMの質が悪い」という誤診から「後処理のフィルタが差し替えている」に修正できた。

### ③ 定義が1箇所か確認する（同じ定数が複製されていないか）

```bash
grep -rn "MY_SCHEMA_VERSION\s*=" src/
```

読み側と書き側に**同じ定数が別々に複製**されていて、片方だけ直しても効かないことがある。
実際、キャッシュキーのスキーマ定数が2ファイルに重複定義されていた。1箇所に統合して解決。

### ✗ 効かなかった方法

- **上位モデル・高性能な依存に差し替える**: 症状が「出力の質が低い」に見えたので、
  LLMを4種（小型モデル / GPT-4o-mini / GPT-4.1-mini / Claude Haiku 4.5）で比較実測した。
  → **有意差なし。しかも3モデルが一字一句同じ文を返した。**
  異なるベンダーの実装が完全一致するのは、原因が自分のコード側（後処理や設定）にある証拠。
  「性能の高いものに変えれば直る」は、原因を特定する前にやると費用だけ増える。
- **コードを丁寧に読み込む**: 3回とも読み込みは十分にやった上で外している。
  読解の精度を上げても、実行されていないファイルを読んでいる限り当たらない。

---

## 予防策（次回これをやる）

調査の最初に、この順で確認する。コードを読み始める**前**でよい。

1. **本当にそのコードが実行されているか** — 目印の文字列を1つ入れて、実行時に届いているか見る
2. **入力と出力が一致しているか** — 途中で誰かが書き換えていないか
3. **定義が1箇所か** — 同じ設定・定数が複製されていないか

「機能フラグがONだから、その経路が使われているはず」は成り立たない（実際に外した）。
フラグの値ではなく、**その分岐に到達しているか**を実測する。

## 実例: 型定義とドキュメントを信じて3回外した（surechigai 2026-08-17）

iOS が「起動時エラー」で却下された調査で、同じ型の誤りを3回繰り返した。
いずれも**実装や実データを見ず、宣言（型定義・ドキュメント・HTTPステータス）で
判断した**もの。

| 信じたもの | 実際 |
|---|---|
| `expo-image` の型定義「alt は accessibilityLabel のエイリアス。Web で alt タグを設定」 | 通常表示の経路は `accessibilityLabel` しか見ておらず、`alt` はプレースホルダー経路専用。**2回デプロイして2回とも効かなかった** |
| 「クエリのタイムスタンプ形式が壊す」と断定 | 事後に同形式の別URLを叩くと正常。壊れていたのは**特定URLに対するCDNのキャッシュ内容**だけ |
| ルートの実在を HTTP 200 で確認 | SPA は**存在しないパスでも 200 を返す**。404画面に対して検査を回していた |

**決め手は毎回「実物を1回見る」だった**。alt は実DOMの属性を数えて、
CDN は実ブラウザの content-type を見て、ルートは本文の文字列を見て確定した。
curl では両方とも正しいJSが返る（ボット判定・キャッシュ差）ため、
**実ブラウザで見ないと分からない**ケースもある。

さらに、この調査で作った**出荷ゲート自体も2回誤った**（誤検知でOK / 誤判定でNG）。
Hermes のバイトコードは文字列テーブルが連結されるため、抽出した「鍵」が
実鍵＋直後の別文字列になっていた。
**判定ロジックを自作したら、通るケースと落ちるケースの両方で検証する。**
片側だけの確認は「動いた」の証拠にならない。
