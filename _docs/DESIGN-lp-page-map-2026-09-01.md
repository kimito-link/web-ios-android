# 設計: kimito-skill.link トップページ改修 —「ヒーローの減量」と「静的な地図」

設計=Fable（claude-fable-5） / 素材収集=マルチLLM会議4体 / 統合・裏取り=司令塔（web-ios-androidリポ担当セッション）
日付: 2026-09-01 ／ 3段構えワークフロー（council-fable）の手順2産物

対象: `site/index.html`（このドキュメント作成時点で904行）

## 背景

ユーザーが別サービス（マーケティング系Podcast LP）のスクリーンショットを示し「そもそもこのLPが
（あの画像の）のようになってない」と指摘。参考画像は「AI目次」（折りたたみ✓箇条書き5項目）を持つが、
kimito-skill.linkはツールキットの入り口であり音声コンテンツの要約とは性質が異なる。ユーザーは
「もっとAIにも人間にも伝わるように会議がいい」と述べ、council-fableワークフローで検討した。

## 会議で判明した決定的事実

**このLPの主要セクション（①〜④ステップ・関連リンク・自動化一覧・ショーケース）は全てJS実行時描画
（steps.js / more-links.js / auto-list.js / showcase.js）であり、JSを実行しないAIクローラーには
空のdivしか見えない。** 静的HTMLとして残っているのはヒーロー・hint-box・claims-box・FAQ・
最終CTAのみ。これが「AIに伝わらない」の実体であり、単なる要約ブロックの有無の問題ではなかった。

## 裁定（会議の対立点への決着）

1. **AI/人間は同じ静的ブロックを読む**（会議の「非対称」説を棄却）。JS描画で不可視な構造を
   埋められるのは静的HTMLの地図だけであり、人間のスキャンと非JS読者への到達を同じ実装で兼ねる。
2. **呼称は「このページの地図」**。参考画像の「AI目次」（折りたたみ）は直訳しない。常時表示の
   フラットな `<nav>` リストにする。
3. **地図は「リンク＋役割1行」**（リンクのみ案を棄却）。ただし**JSON駆動セクションの中身
   （個々のカードタイトル）は書かない**——地図とJSONの二重管理を避けるための鉄則。
4. **優先順位は①ヒーロー整理→②地図追加**。過積載のヒーローに地図を足すだけでは逆効果。
5. **「品質より伝わり方」原則の一文はヒーローから削除**（会議未決着分の司令塔+Fable裁定）。
   思想の解説は `learnings/` が既に受け皿として存在するため、LPへの再配置はしない。

### C-2. page-map（新規ブロック）

配置: hint-box閉じタグの直後、`data-shindan-version-summary`の直前。

```html
<!-- このページの地図：全セクションの位置と役割の静的インデックス。
     ①〜④カード・関連リンク等はJS描画のため、非JS読者(AIクローラー)には
     この地図が唯一の全体構造情報になる。静的HTMLのまま維持すること。
     行はHTML上のセクションと1対1。JSON(steps.json等)の中身は書かない。 -->
<nav class="page-map" id="page-map" aria-label="このページの地図">
  <div class="page-map-title">🗺 このページの地図</div>
  <ul>
    <li><a href="#steps">やることは①②③④だけ</a><span>使い方の必須手順とおまけ機能</span></li>
    <li><a href="#ai-start">AIに渡す文章</a><span>コピペで作業を始める開始文</span></li>
    <li><a href="#claims">できること・できないこと</a><span>自動/一緒に/人の作業の正直な区分け</span></li>
    <li><a href="#more">もっと知りたい方へ</a><span>お店ごとの手順・困りごと別の詳細ページ</span></li>
    <li><a href="#auto">自動でやってくれること一覧</a><span>肩代わりされる作業と実測パネル</span></li>
    <li><a href="#showcase">実際に使った例</a><span>このキットで公開したアプリ</span></li>
    <li><a href="#faq">よくある質問</a><span>経験の要否・全自動かどうか・審査のこと</span></li>
  </ul>
</nav>
```

CSSは2カラムグリッド（`@media (max-width:900px)`で1カラム）。デスクトップで4行分以内に収める
（地図自体が重いセクションにならないこと）。行文に数値（枚数・分数）を書かない。

## D. MVP

**ヒーロー整理（C-1）を先に単独でデプロイ**。地図（C-2＋C-3）は第2コミットとして続けて入れる。

## E. 捨てた案と理由

1. AI目次の直訳（折りたたみ✓箇条書き） — 非JS読者に閉じた状態で届き、静的地図の存在理由と矛盾
2. ヒーロー直上のAI Summary（結論・主張・行動・価値の4項目） — hint-box・h1・DLボタンと重複
3. AI向け別チャネル拡充（JSON-LDへのセクション構造追加） — 静的navが両方に効くため二重管理
4. 地図のJSON駆動化 — 7行にレンダラは過剰設計
5. 地図に個々のカードタイトルを列挙 — 地図とJSONの二重管理になる
6. 地図リンクのみ（1行要約なし） — 非JS読者にセクションの役割が伝わらない
7. 「品質より伝わり方」原則のLP内再配置 — ヒーローの1つの約束に集中するため削除で確定

## F. 地雷と回避策

1. `verify-internal-links.mjs`は同一ページ内`#anchor`のid実在を検査する。地図の7リンクとC-3の7id
   は**同一コミットで**入れること。
2. `verify-claims-coverage.mjs`のRULE 1は`site/index.html`の静的文字列検索。`.claims-box`は
   `id="claims"`の属性追加以外一切触らない（JS描画化は禁止・既に判明済みの制約）。
3. `npm run claims:provenance`（数値主張の出典コメント検査）: 地図の行文・縮小後のヒーロー文言に
   新しい数値を書かない。C-2の文面は数値ゼロで設計済み。
4. 「編集した≠反映された」: `git push`だけでは本番に出ない。`npm run deploy:site`を手動実行し、
   本番URLを実際に開いて地図が見えることを確認してから完了報告する。
5. ヒーロー削除時、`learnings/#multi-session`等のリンクは削除ではなく移設。リンク自体を消すと
   導線が死ぬだけでゲートは沈黙するので注意。
6. `id="faq-title"`は改名・削除しない。他ファイルからの参照は検索済みで無し（実測確認済み）。
7. ビルドツールなし: 地図はHTML直書き・CSSは`index.html`内`<style>`への追記のみ。
