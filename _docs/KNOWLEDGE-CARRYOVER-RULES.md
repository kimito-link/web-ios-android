# 知見の書き戻しルール（AIへ）

> このキットは「読むだけ」で終わらせない。新しいアプリの提出で得た知見は、
> 次のアプリの提出で自分（AI）が読み返せる形で、このキットに書き戻す。

---

## いつ書き戻すか

以下のいずれかが起きた直後（作業が一区切りついたタイミング）に、知見を書き戻す。

- ストア審査で **却下された**（Guideline番号・却下理由が分かった）
- CIやビルドで **初めて見るエラーに当たり、原因を特定して直した**
- 「毎回同じ質問をユーザーにしていた」ことに気づいた（＝確定事実化すべき情報）
- 既存の `_docs/*.md` の記述が**実際の挙動とズレていた**（設定値・手順が古くなっていた）

逆に、次のような場合は書き戻さない（ノイズになる）:
- 既存KBの記述通りに一発で解決した（学びがない）
- アプリ固有の値（ドメイン名・パッケージID等）しか変わらなかった

## どこに書き戻すか

| 起きたこと | 書き戻す先 |
|---|---|
| App Store 却下 | `_docs/apple-reject-knowledge-base.md` |
| Google Play 却下・審査詰まり | `_docs/google-play-submission-playbook.md` |
| 新規アプリの「初回だけ」出るブロッカー | `_docs/FIRST-SUBMISSION-blockers.md` |
| CI/リリースパイプラインの詰まり | `_docs/release-pipeline-playbook.md` |
| 上記に当てはまらない新種の知見 | 新規ファイルを `_docs/` に作成し、`CLAUDE.md` の表に1行追加してリンクする |

既存ファイルに追記するときは、そのファイルの既存フォーマットに合わせる
（`FIRST-SUBMISSION-blockers.md` なら「症状／原因／直し方」の3点セット、など）。
書式を勝手に変えない。

## 書き方の最低ライン

1. **症状**: 実際に出たエラーメッセージ・ログの文言をそのまま引用する（grepで引っかかるように、要約しない）。
2. **原因**: なぜ起きたか。設定ミスなら「何を何だと思い込んでいたか」まで書く。
3. **直し方**: 実際に効いた手順。試して効かなかった方法があれば、それも「✗ 効かなかった」として残す
   （次に同じ罠を踏んだときに同じ回り道をしないため）。
4. どのアプリ・いつの実戦で得た知見かを1行添える（`_docs/` の既存ファイルの書式を参照）。

## 書き戻したら

- `CLAUDE.md` の該当テーブル行を、新しい詳細に合わせて更新する（説明文が古くなっていないか）。
- 既存の記述と矛盾する内容になった場合は、古い記述を消して1つの正しい状態にする。
  「念のため両方残す」はしない（AIが次に読んだときにどちらが正か分からなくなる）。
