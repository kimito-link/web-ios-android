## 1. 事故A: ログイン済み判定の偽陽性（最初に踏む・最も危険）

**症状**: 認証状態保存スクリプトが「ログイン完了」と表示するのに、実際には未ログインのまま
保存されている（`cookies: [], origins: []`の空ファイル）。以後、この空ファイルを使う全ての
E2E検証がゲスト状態のまま走り続け、「ログイン込みで検証したつもり」が実は一度も検証できていない。

**原因**: ログイン済みかどうかの判定を「ゲスト向け案内文言が非表示になったこと」のような
間接的なシグナルに頼ると、ページロード中など未ログイン以外の理由でも文言が消えて見える瞬間があり、
**Xログインを一切せずに数秒でテストが「成功」と誤判定される**。

**直し方（唯一の正解）**: ログイン判定は、**「その状態でしか絶対に真にならない」直接シグナル**を使う。
Clerkの場合は認証Cookie `__client_uat`（Unix秒のタイムスタンプ）。値が`"0"`ならゲスト、
`"0"`以外なら確実にログイン済み。中間状態が存在しないので偽陽性が構造的に発生しない。

```js
async function readClerkCookies(context) {
  const cookies = await context.cookies().catch(() => []);
  const uat = cookies.find((c) => c.name.startsWith("__client_uat"));
  return { loggedIn: Boolean(uat && uat.value && uat.value !== "0") };
}
```

**さらに一段防御**: 「検知成功するまで保存ファイルを一切書かない」設計にする。
判定ロジックにもし将来バグが混入しても、空ファイルという中途半端な状態そのものが発生しなくなる。
保存後は別のヘッドレスブラウザで実際に読み込み、`window.Clerk.user`が復元できるかまで検証してから
「成功」を宣言する（=「保存できた」ではなく「使える」ことを確認する）。

## 2. 事故B: QA検証ツールが実際のユーザー導線と違うURLを叩いていた

**症状**: 「1タップXログインが効いていない」というユーザー報告。調査してもアプリ本体のコードは
どこもおかしくない。

**原因**: Clerk標準の`<SignIn/>`に対して、「Xボタンへ自動でclickイベントを1回送る」という
1タップ化コンポーネント（`AutoAdvanceToX`的なもの）を実装している場合、その自動発火は
**特定のURLクエリパラメータ（例: `?auto=x`）が付いているときだけ**動く設計になっているのが定石
（ボタンのclickを横取りせず、標準の`<SignIn/>`はそのまま保つ安全な実装パターンのため）。
QA検証スクリプトがこのパラメータを付けずに`/sign-in`へ直接アクセスしていたため、
1タップ導線が発動せず、素の2タップ画面が表示されていた。**アプリは無罪、QAツールのURLが
実際のCTAボタンの導線と食い違っていただけ。**

**直し方**: QA/E2Eツールが叩くURLは、**アプリのCTAが使っている定数を直接importする**。
手書きしない。Playwright specなら`import { SIGN_IN_AUTO_X_HREF } from "../../lib/clerk-route"`
のように、単一のソース・オブ・トゥルースを共有する。`.mjs`スクリプト等でimportできない場合も、
値をコメントで出典明記した上で、定数とテストで同期を強制する（定数が変わったらテストも落ちる形にする）。

**チェックリスト（QAツール新規作成時に必ず確認）**:
1. URLを手書きしない。アプリのCTAが使う定数をimportする。
2. クエリパラメータまで一致させる（同じパスでも自動化フラグの有無で挙動が変わる）。
3. どのユーザー導線を再現しているかをスクリプト冒頭コメントに明記する。
4. 導線の変更はテストも追随させる（CTAのhrefを変えたら整合テストで検知できる形にする）。

## 3. 事故C: タイムアウトしても「何が起きていたか」が一切分からない

**症状**: Xログイン画面を自動で開いて完了を待つ設計にしたところ、5分間「未検知」のまま
何も変化せずタイムアウトした。ユーザーが放置していたのか、エラーが出ていたのか、
2要素認証で詰まっていたのか、全く分からないまま失敗として終わる。

**直し方（3点セット。会議ハーネス+Fable設計で確立）**:

1. **証跡の自動収集（判定条件とは完全に分離する）**: ログイン待機中、以下を裏で収集する。
   判定ロジックには一切混ぜない（事故Aの教訓＝判定は単一の直接シグナルのまま保つ）。
   - `timeline.ndjson`: URL遷移・画面の説明・console error・pageerror・page crash を、
     発生の都度1行ずつ即時フラッシュで記録（プロセスが途中で死んでもここまでのデータは残る）。
   - `shots/`: 30秒毎のスクリーンショット（人間の操作速度なので30秒で十分。機械的な
     初回クラッシュ検証など秒単位の現象を追う場合は2秒毎などもっと高頻度にする）。
   - タイムアウト確定時: 最終スクリーンショット + DOMダンプ(`page.content()`)。
   - **`page.context().tracing`は使わない**: (1) X等のパスワード入力画面まで記録してしまう
     プライバシー問題、(2) `tracing.stop()`まで書き出されずプロセス途中死で消える、
     (3) zipが大きい。ndjson+都度スクショの方が軽く、途中死に強い。

2. **アイドルベースのタイムアウト延長**: 全ページ（外部のOAuthプロバイダのドメインも含む）に
   `keydown`/`pointerdown`の最終時刻を記録する`addInitScript`を注入する。期限到達時、
   直近1分以内に操作があれば締切を自動延長（例: 2分刻み、絶対上限15分）。
   2要素認証やCAPTCHAで手間取っているだけの正常な操作を、固定タイムアウトで打ち切らない。
   逆に本当に放置されている場合は既定時間（例: 5分）で早期に確定し、証跡付きで失敗を返す。

3. **タイムアウト時の「詰まりどころ」自動推定**: 最終URLのホストと`document.body.innerText`から
   仮説を立てる（あくまでヒューリスティクスであり確定診断ではないと明記する）。
   - OAuthプロバイダのドメイン + 「認証コード」「verification code」等の文言 → 2要素認証で停滞
   - OAuthプロバイダのドメイン + 「エラー」「制限」「try again」等の文言 → プロバイダ側の
     エラー/レート制限（**このキットで実際に踏んだ。§5参照**）
   - 自社の`/sign-in`のまま外部に遷移していない → 自動化フラグの空振り疑い
   - about:blank → ネットワーク断

## 4. 事故D: Windows固有のspawn罠（子プロセスでnode/npm/pnpmを起動する全スクリプト共通）

**症状**: 「'C:\Program' は、内部コマンドまたは外部コマンドとして認識されていません」という
エラーで、対話式ランチャースクリプトの子プロセス起動が即失敗する。

**原因**: `child_process.spawn(cmd, args, { shell: true })`をWindowsで使うとき、
`cmd`（例: `process.execPath` = `C:\Program Files\nodejs\node.exe`）がスペースを含む場合、
`shell:true`はコマンド文字列をそのままcmd.exeに渡すため、クォートしないと`C:\Program`だけが
実行ファイル名として解釈されて壊れる。

**直し方**:
```js
const quoteWin = (s) => (/[\s]/.test(s) ? `"${s}"` : s);
const isWin = process.platform === "win32";
const child = spawn(
  isWin ? quoteWin(cmd) : cmd,
  isWin ? args.map(quoteWin) : args,
  { shell: isWin, windowsVerbatimArguments: isWin, /* ... */ },
);
```
cmd・argsとも、スペースを含み得るものはダブルクォートで囲み、`windowsVerbatimArguments: true`を
併用する（Node側の自動クォート処理との二重適用を避けるため）。
**このキットのスクリプト群（`templates/scripts/*.mjs`）がWindowsから実行される限り、
新しく`spawn`/`exec`を書く箇所は必ずこのパターンを踏襲する。**

## 5. 事故E: OAuthプロバイダ（X）側のレート制限で長時間ブロックされる

**症状**: 「ログインを一時的に制限しました。しばらくしてからやりなおしてください」という
表示がX側に出て、以降ログイン試行そのものができなくなる。アプリ側・QAツール側のコードは
無関係で、直せない。

**原因**: 同一環境（同じIP・同じブラウザプロファイル）から短時間に何度もOAuth認可画面へ
遷移する自動テストを繰り返すと、X側がbotっぽいアクセスとして一時的にブロックする。
1タップ導線の常設E2Eテスト（`tests/e2e/login-one-tap-x.spec.ts`のような、実際に
Xボタンをclickさせてナビゲーションを検証するテスト）を何度も実行すると、特に踏みやすい。

**回避策（実装済み・このキットにも横展開すべき）**:
- 1タップ導線の常設E2Eテストは、**実際にX側へナビゲーションさせず、`route.fulfill({status: 204})`で
  X向けのリクエストを直前でブロックする**設計にする。ブラウザは204を受けてナビゲーションを
  中止するため、X側には一切リクエストが届かない（レート制限を踏まない）。
  それでいて「Clerkの標準ボタンへ実際にclickが送られ、ナビゲーションが試行されたか」という
  本体の検証はできる（fakeボタンで試行を記録するより本番に忠実）。
  ```js
  await page.route("https://x.com/**", async (route) => {
    oauthRequests.push(route.request().url());
    await route.fulfill({ status: 204, contentType: "text/plain", body: "blocked" });
  });
  ```
- 逆に、**認証状態を1回だけ人間が保存する`e2e:auth-save`的なスクリプトは、実際にX認可画面まで
  進む必要がある**（bot対策のため自動化できない）。これは「何度も繰り返す自動テスト」ではなく
  「人間が実行するたび1回だけ」なので通常はレート制限を踏みにくいが、**短時間に何度も
  やり直すとこちらも踏む**。踏んだら技術的な解決策はなく、時間を置くしかない
  （目安は数十分〜数時間、確実な時間は不明）。デバッグ中に「うまくいかないから何度も
  すぐ再実行する」を繰り返すと自ら踏みに行く結果になるため、**1回失敗したら最低でも
  相応の待ち時間を置いてから次を試す**運用ルールにする。

## 6. 「確認させない最大化」の3層モデル（設計の型）

上記の教訓を、汎用的な設計原則として抽出したもの。Clerk/X以外のOAuth（Google/Apple等）や、
このキットの他の自動化（App Store/Google Play提出等）にも同じ型が使える。

| 層 | 意味 | 対応 |
|---|------|------|
| A. 聞かない | 確認プロンプト・メニュー選択を出さない。実行するだけで最後まで進む | 対話メニューをやめ、`--only=xxx`のようなフラグで個別実行できる形は残しつつ、既定は全自動フローにする |
| B. 待たせない | 人間にしかできない操作の待ち時間中、無駄な直列待機を作らない | ログイン不要な検証を先に全部済ませておく等（ただし計測系の並列実行は負荷競合で計測が歪むリスクがあるため、人間待ちとの重ねに限定する） |
| C. 聞き返さない | 失敗しても人間に「何が起きたか」を質問せず、証跡から自己診断して報告する | §3の3点セット（証跡自動収集・アイドル延長・詰まりどころ推定）+ 全体結果の先頭に「総合判定: OK/NG — 理由」を1行で出す |

**却下した案（過剰実装として見送ったもの）**:
- Playwright `tracing`の常時記録（プライバシー・途中死・サイズの3点で不利、ndjson+都度スクショで代替可能）
- 有効期限メタファイルの新設（cookieの`expires`とファイルのmtimeで十分、ファイルを増やすと分岐が増えるだけ）
- 認証情報自体の自動入力・保存（bot対策・2要素認証・規約リスク。本人操作は最後まで残す）

## 7. このキットへの適用余地（次にやるなら）

  §1のCookie直接判定パターンが使われているか確認し、間接シグナル判定になっていないか点検する。

  汎用スクリプトとして用意しておけば、新規アプリを立ち上げるたびに車輪の再発明をしなくて済む。
- §5のレート制限対策（route interceptでのブロック）は、Xに限らずGoogle/Apple OAuthの
  E2Eテストを書く場合にも同じ設計を踏襲すべき。
