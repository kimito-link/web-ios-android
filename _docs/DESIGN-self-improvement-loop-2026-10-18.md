## 1. 一言で
プログラムの症状を集め、AIが「原因の仮説」と「版の提案」を書き、人間が承認し、各プロジェクトのいつもの出荷手順（1版1変更・テスト・検証ゲート）で出す。
AIは提案するところまで。プログラム自身が自分のコードを書き換えることはしない。ストアや本番には入れず、ローカルPCだけで動く。

## 2. 流れ（どのプロジェクトでも同じ）
1. **症状の入口（アダプタ）**: そのプロジェクトの診断・ログ・状態速報・テスト失敗・CIログ・ユーザー報告を読む。読むだけで何も変えない。
2. **症状カードを作る**: 匿名化・集計済みのプレーンJSON。機械が作る（AIには作らせない）。
3. **ローカルAI（Ollama）が提案書を書く**: 原因仮説と版の提案を Markdown で。
4. **人間が読んで、承認・却下・保留を台帳に記録する**。
5. 承認された提案だけ、実装ハンドオフにして別モデルが実装する。
6. そのプロジェクトの出荷ゲートを通して、1版1変更で出す。
7. 次の症状入口で効いたかを測る（1に戻る）。

## 3. 決定事項（2026-10-18 本人決定）と、絶対に守ること

**決定事項**
- AIは最初はローカル（Ollama・127.0.0.1）だけを使う。Claude などの外部AIには、当面なにも渡さない（渡す運用は、ローカルAIの質が足りないと分かってから改めて決める）。
- 代替（ローカルAIの質が足りないとき）: 人間が症状カードを選んで Claude に貼る半自動運用。この場合も本設計は成立する。
- 範囲: 特定の拡張やコメントのデータに限らず、すべてのプログラムが対象。
- ★この「外部AIに渡さない」は**このループの中だけ**の決定。キット全体のマルチ頭脳運用（Grok/Qwen 等へ手を動かす仕事を投げる）を変えるものではない。

**絶対に守ること（全プロジェクト共通）**
1. ストア・本番の出荷物に入れない。ループはローカルPC上のスクリプトとファイルだけで完結。出荷物にAI送信コードを足さない。
2. プログラムが自分のコードを書き換えない。外から取ったコードを実行しない（ストアの外部コード実行禁止。[§5-3 の 2.5.19](../docs/ai-rules/01_CORE_RULES.md) とも整合）。
3. 人や取引に関わる実データを外部へ送らない。コメント本文・ユーザーID・名前・メール・電話・住所・アイコンURL・決済情報・配信ID・端末識別子など、利用者や第三者に結びつく情報はすべて対象。
4. 秘密値（APIキー・トークン・接続文字列）を、症状カード・提案書・ログ・チャットに残さない。鍵の変数名も含めない。
5. 特定のAIベンダーに依存しない。入力はプレーンJSON、出力は Markdown。
6. AIの出力は「仮説」。証拠（実測・差分・テスト）が付くまで事実にしない。
7. 承認は人間が文字で出す。AIの提案・AI同士の合意・サブエージェントの報告は承認ではない。
8. 既存の部品を使う。新しい巨大機構は作らない。
9. 各プロジェクトの個別ルール（AGENTS.md・CLAUDE.md）が優先。ループはそれを緩める方向には働かない。

## 4. 部品（最小・すべてローカルのスクリプトとプレーンファイル）
1. **アダプタ**（プロジェクトごとに1つ）: 症状の入口を読んで共通の「症状カード」形式に変換する。ここだけがプロジェクト固有。
2. **症状カード**: `_loop/<プロジェクト名>/symptoms/<日時>-<症状ID>.json`（git管理外）
   - 含める: 症状ID・判定結果・版・ビルドID・数値（件数・ms・段別の人数などの集計）・時刻。含めない: §3-3 の実データ全般と鍵。
   - **マスクは許可リスト方式**（出してよいフィールド名だけ列挙し、それ以外は落とす）。禁止リスト方式にしない（新しいフィールドが増えても漏れないため）。
3. **提案書**: `_loop/<プロジェクト名>/proposals/<連番>-<要約>.md`
   - 形式は固定: 症状 / 観測（症状カードの数値だけを根拠に）/ 原因仮説（複数・確度つき・反証方法つき）/ 版の提案（1版1変更・触るファイル候補・やらないこと）/ 検証手順。
   - 「確証」と「推測」を分けて書かせる。根拠のない断定は無効。
4. **承認台帳**: `_loop/<プロジェクト名>/decisions.jsonl`（1行1件・追記専用）
   - `{id, proposal, decision: approved|rejected|deferred|no_effect, by, at, reason}`
   - AIが書けるのは proposed まで。approved は人間の文字のあとにだけ書く。却下の理由も、効かなかった提案（no_effect）も消さずに残す。
5. **ランナー**: 横断の置き場に薄く1つ。アダプタ呼び出し → 症状カード検査 → **ローカル Ollama を HTTP で直接呼ぶ（§0 の訂正。dispatch.py は使わない）** → 提案書の形式検査、を順に呼ぶだけ。
※ `_loop/` は git 管理外（実データが混ざりうるため）。リポに置くのは、形式の仕様書とアダプタのコードだけ。100年後に読めるのは仕様。**`.gitignore` への `_loop/` 追記も実装時の必須項目**（まだ入っていない）。

## 5. 送る/送らないの線
- 症状の入口の読み取り: 各プロジェクトの既存の経路をそのまま使う。変えない。
- 症状カード作成・提案書・承認台帳: ローカルPCのみ。AI呼び出し: ローカル（Ollama）固定。外へ出ない。
- 症状カードに許可外のフィールドが混ざったら、作成を失敗させる（fail-closed）。

## 6. 実例（Chrome拡張で確認された、アダプタを書くときの注意）
- 状態速報（`status:live`）には、第三者のコメント本文・ユーザーID・名前・アイコンURLが入る。`commentTimelineMirror` の各行は `{at, name, text, avatarUrl, userId, kind}`（`src/lib/commentTimelineMirror.js:15`）。laneMirror・northStarMirror・topSupporters・giftHistoryMirror・lives[] も名前・IDを含む可能性が高い（実フィールド名は未精査）。→ 速報をそのままAIに渡さず、許可リスト方式で数値と症状IDだけを抜く。
- 症状から根本原因への機械テーブルは無い。症状カードに原因候補IDは持たせず、仮説は提案書側に置く。
- AGENTS.md は `NL_STORE_BUILD=1` を必須と書くが `scripts/build.mjs` に実行コードの参照は無い。ストア版を守る実際の防壁は `stage-submission.py` の `verify_no_secrets`（鍵と manifest の key しか見ない）。出荷物にコードを足さない本設計では影響しない。
- ※この節の事実は貼り付け元のセッションの記述で、このセッションでは Chrome 拡張のコードを読んでいない（**未検証**）。

## 7. 100年持たせるための決め事
- 形式が主、AIは従。症状カード=JSON、提案書=Markdown、台帳=JSON Lines。
- 各ファイルに schema 番号を持たせる。変えるときは追記で足し、古い版も読めるようにする。
- AIの名前を処理の条件にしない。「どのAIが書いたか」はメタ欄として残すだけ。
- **判定はコードに置き、文書に置かない**。許可リスト・形式検査・承認の必須化はテストで固定する（元に戻すと赤くなる）。
- 計器を足して満足しない。ループの価値は「直った版が増えたか」だけで測る（提案の件数は成果ではない）。
- 正本は1つ（この文書）。各リポには橋渡し1行だけ置く。

## 8. 失敗したとき（fail-closed）
- AIが形式外の提案書を返した: 形式検査で却下し、台帳に `rejected(format)`。人間に渡さない。
- AIが落ちた・動かない: 外部AIへ自動で落とさない。止まって人間に知らせる。
- アダプタが許可外のフィールドを通そうとした: 症状カードの作成を失敗させ、AIへ渡さない。
- 同じ症状の提案が繰り返される: 却下理由と照合し、却下済みと同趣旨なら提案書に「却下済み: <id>」と明記させる。
- 実装したが効かなかった: 次の症状入口で測り、台帳に `no_effect` を追記する。

## 9. やらないこと
プログラムの自己書き換え・自動マージ・自動配置・自動ストア提出／AIによる承認・AI同士の相互承認／利用者や第三者の実データを使った分析／他人（利用者）へ配る機能化（する場合は別設計。プライバシー開示を同時に更新し、既定OFF・明示的な手動オプトイン）／新しいクラウド基盤・常駐サーバーの追加／数値台帳への提案・仮説の混入。

## 10. 最小の最初の一歩（MVP）
1. 症状カードの共通スキーマと許可リスト検査を決める（仕様書＋テスト。プロジェクトに依存しない形）。
2. アダプタを1つだけ作る（Chrome拡張の `status:live --json` → 症状カード。AI不使用・機械のみ）。
3. 提案書の形式検査（AIなしで、手書きの提案書でも通る/落ちるをテスト）。
4. 承認台帳の追記スクリプト（approved は人間の文字が要る）。
5. そのあとで初めて、ローカル Ollama（HTTP直叩き・道具なし）で提案書を書かせる。
6. 2つ目のプロジェクトのアダプタで、ループ本体を変えずに動くことを確かめる（共通化できている証拠）。
