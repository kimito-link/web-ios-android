# ローカルAIによる提案書づくり（自己改善ループ 第5歩）仕様と実測 v1

> **今の到達点: 実装完了（動く）・提案書の質は未達（このPCの今の条件では、質の出る大きさのモデルが実用速度で動かない）。**
> 親: [`DESIGN-self-improvement-loop-2026-10-18.md`](DESIGN-self-improvement-loop-2026-10-18.md)。前提の仕様: [`SPEC-symptom-card-v1.md`](SPEC-symptom-card-v1.md)・[`SPEC-loop-ledger-and-proposal-v1.md`](SPEC-loop-ledger-and-proposal-v1.md)。
> 実装: `templates/scripts/loop-propose.mjs`（CLI）・`templates/scripts/lib/loop-propose-core.mjs`（純関数）・テスト `loop-propose-core.test.mjs`。

## 何をするか
`node scripts/loop-propose.mjs --project <名前> --cards <カードの置き場> --model <Ollamaのモデル名> [--glossary <用語集.txt>] [--out <提案書の置き場>] [--ledger <decisions.jsonl>]`
1. カードを読み、**症状カード検査に通ったものだけ**を使う（1枚でも違反したら何も送らない）。
2. プロンプトを組む（規則＋任意の用語集＋カードのJSON＋書く型）。**送り先はローカルだけ**（`127.0.0.1`/`localhost`/`[::1]`以外は拒否。`dispatch.py` は使わない）。Ollama の `/api/chat` を道具なし・1回だけ呼ぶ（ストリーム受信）。
3. ヘッダー（schema・proposal・project・cards・writer）は**機械が付け**、モデルには5つの節の本文だけを書かせる。思考ブロック・コードの囲み・前置きは落とす。
4. 提案書の形式検査（`proposal-format-core`）。通れば `proposals/` に置き、台帳に `proposed`（`ai:<モデル>`）を追記。通らなければ `proposals/_invalid/` に違反一覧と置く（**台帳には書かない**＝台帳は人間の決定の記録。設計 §8 の「台帳に rejected(format)」からの意図的な修正。機械の却下は台帳に混ぜない）。
- 終了コード: 0=置いた / 1=カードまたは提案書が検査に通らない / 2=測れていない（Ollama に届かない・引数不足）。外部AIへは落とさない。

**用語集（`--glossary`）**: 症状IDの意味のような**固定の知識**。カード（データ）とは別に渡す。秘密・メールらしき形と 4KiB 超は拒否。実測で、無いと症状IDの意味を取り違える（下記）。プロジェクト側のアダプタが、自分のコードから自動生成する（tsuioku は `scripts/loop-glossary-status-live.mjs`）。
**`--repo <対象リポ>`**: 提案書の「触るファイル候補」が `git ls-files` に実在するか照合する（創作の防止）。

## 実測（2026-10-18・このPC: RTX 4070 Ti 12GB / RAM 80GB）
| 項目 | 結果 |
|---|---|
| **GPUの空き** | 何もモデルを載せていない状態でも **6.2GB を他のアプリが使用**。モデルに使えるのは約6GB |
| 7B（`wwhite/whiterabbitneo-v3-7b:q4_k_m` 4.4GB） | 生成 **23 token/s**・プロンプト 387 token/s。提案書1通 **7〜30秒** |
| 14B（`qwen2.5:14b` 9.5GB） | **0.7〜1.2 token/s**（GPUに載りきらず溢れる。`ollama ps` は「100% GPU」と出るが実速は桁違いに遅い）。提案書1通は10分超で実用外 |
| 35B MoE（`qwen3.6:35b-a3b` 22GB・CPU59%/GPU41%） | 暖機後も **1.3 token/s**・プロンプト 9 token/s。1通 約20分で実用外 |
| 形式検査の合格（7B・合成カード2種×各2回） | **4/4**（用語集ありの1回も合格） |

**中身の質（7B・n=5回の目視）**: 形式は通るが**質は低い**。
- 用語集なし: 「thumb-white が fail → thumb-white を ok に変更する」という**循環**、観測の数字を【確証】と呼ぶ誤用、道具の名前（status-live-adapter）を製品と取り違え。
- 用語集あり（1回）: 循環は消え、【確証】の使い方も正しくなったが、仮説は一般論で、「変更」と「やらないこと」が矛盾した。
- ＝**形式検査は「形が整っている」ことしか保証しない。質の判定は人間の承認（設計 §3-7）が要る**。n が小さく、モデルも小さいので、「ローカルAIでは無理」とも「用語集で足りる」とも**言えない**。

## 用語集の自動生成と、機械の検査を足した後の実測（2026-10-18・同じ7B・合成カード2種）
- **用語集を自動生成**（拡張側 `scripts/loop-glossary-status-live.mjs`・tsuioku。症状7個の名前と「次の一手」をコードから読む）。7B の仮説が、拡張自身の「次の一手」に沿うようになった（例: レーンが空 → 供給側(heavy/鏡)を確認）。ただし多くは用語集のなぞりで、仮説の深さは増えていない。
- 実測で見つかった**モデルの失敗が2種**。どちらも内容の検査ではなく**形・事実の検査**で防げるので、機械に足した:
  1. **存在しないファイル名の創作**（`heavy.js`・`mirror.js`）→ `--repo <リポ>` を渡すと、「触るファイル候補」のファイル名が `git ls-files` に実在するかを照合し、無ければ `file-not-found(<名前>)` で拒否。
  2. **雛形の穴埋めの置き忘れ**（`(ファイルやモジュール名)` を6回中3回そのまま出した）→ 雛形の穴埋めを `SKELETON_PLACEHOLDERS` に一元化し、残っていたら `placeholder-not-replaced(<穴埋め>)` で拒否（雛形と検査が同じ一覧から作られるのでずれない。テストで固定）。
  - 末尾に付く英語の挨拶（"Please let me know…"）も整形で落とす。
- **ガード後の実測（8回）**: シナリオA（症状1つ）4/4 合格。シナリオB（症状2つ）**0/4 合格**（穴埋め残り1・創作ファイル3）＝**ガードが、人間に渡る前に、実際のモデルの失敗を止めた**。
- 限界: ファイル照合は、**ファイル名を書いたときだけ**効く。ファイル名を書かずにぼかす（「関連するコード」）提案は通る（それは質の問題で、人間が判断する）。

## 診断用の用語集の自動生成と実測（2026-10-18・同じ7B・合成の診断結果＝2検査が失敗・1検査が測れず）
- **生成**: `templates/scripts/loop-glossary-diagnostics.mjs --project <名前> [--dir <検査の場所>] [--cards <カード>]`。各検査(check-*.mjs)の**先頭コメント**から「何を見る検査か」を1文取り出し（書式の違い4種に対応・最大48字）、診断カードの固定の説明（`CARD_GLOSSARY`）と合わせる。`--cards` で、カードに出る検査だけに絞れる（検査が多いプロジェクトで4KiBを超えるとき）。書く前に用語集の検査（秘密・メール・4KiB）を通す。説明が取れない検査は「説明が書かれていない」と書く（作り話をしない）。
- **このキットの全26検査から説明が取れる**（テストで固定。先頭コメントの書き方が変わったら赤）。全検査の用語集は 約3.6KB で上限に収まる。
- **効果（各3回・形式検査は6/6合格。中身を集計）**:
  | | 用語集なし | 用語集あり |
  |---|---|---|
  | `check-doc-rot` を「ドキュメントのローテーション」と誤読 | **3/3** | 1/3 |
  | 道具（診断アダプタ）を製品と取り違える | **3/3** | 0/3 |
  | 指示書（CLAUDE.md）に言及＝意味を理解 | 0/3 | **3/3** |
  - 用語集ありで、触るファイル候補に実在する `CLAUDE.md` を書いた（`--repo` の照合を通過）。
- **限界**: 7B 1種・合成カード1種・各3回。仮説は検査の説明を言い換えたものが多く、**因果の深さは増えていない**。「確証」の誤用も残る（例: 「指示書の形式が正しくない」と断定したが、カードは「検査が失敗」としか言っていない）＝人間の承認が要る。先頭コメントが「なぜ作ったか」から始まる検査（`check-instruments-reachable`・`check-heartbeat-present` など）は、説明が「何を見るか」から外れる。

## 一般用途の7Bの導入と、「実在するファイルの候補」を渡す変更（2026-10-18）
- **`qwen2.5:7b-instruct` を導入**（約4.7GB・Ollama 公式レジストリ・本人の許可のうえ）。速度は **毎秒68トークン**（セキュリティ特化の7Bは同じ条件で23）。`loop.config.json.example` の既定モデルにした。
- **最初の結果（9回）: 形式検査の合格は 1/9**。落ちた理由はほぼ全部、**存在しないファイル名の創作**（`scripts/check-doc-rot.py` のように、実在は `templates/diagnostics/check-doc-rot.mjs`）。検査は正しく止めたが、止めるだけでは提案書が出ない。
- **対処: `--repo` を渡すと、カードの症状IDに関係する実在ファイルの名前（最大12件）をAIに渡し、「触るファイル候補はこの一覧から選ぶ。合うものが無ければ（ファイル名は未確認）」と指示する**（`pickCandidateFiles`・名前だけで中身は渡さない）。関連の見つけ方は、ファイル名がカードID/検査名と一致 → コードの中にIDの文字列がある → テスト、の順。
- **効果（同じ9回ずつ・各モデル）: qwen2.5:7b-instruct 1/9 → 8/9、セキュリティ特化の7B 8/9。** 残りの失敗は、穴埋め `（…）` の置き忘れ1件と、通信の1回失敗。
- **その中身を読んで見つけた問題を2つ直した**（すべてテストで固定）:
  1. 「測れなかった（unmeasured）」を不具合と取り違え、失敗している検査でなく測れなかった検査を直す対象に選ぶ → 規則に「直す対象は fail を優先、unmeasured は別扱い」を追加。診断シナリオで、失敗した検査を正しく選んだのは **0/3 → 1/3**（部分的な改善）。
  2. **道具そのもの**（`loop-adapter-*.mjs` 等）や、土台のカード（`status-snapshot`・`diagnostics-summary`）に引っかかり、「道具を直す」提案になる → ループの部品（`loop-*.mjs`・`loop.config.json`・`_loop/`）と土台のカードidは、候補探しに使わない。拡張の速報では、道具のファイルが消えて実在の製品ファイル（`src/extension/status-entry.js`）になった。テストが、テストファイル（`loop-…test.js`）が除外をすり抜ける抜けも見つけて直した。
- **限界（正直に）**: 7B の提案の**中身は、まだ質が低い**（根拠のない変更案「`livesCount` の閾値を2に上げる」、実装が不完全という憶測、など）。形式・ファイルの実在・道具の取り違えは機械で防げたが、**因果の深さと妥当性は、人間の承認の仕事**のまま。n は各3回・合成カード2種。

## 分かったこと（設計への反映）
1. **ローカルAIの実効サイズは、そのPCのGPU空きで決まる**。他のアプリが6GB使っている間は 7B まで。大きいモデルは、GPUを使うアプリを閉じて空きを作るか、別マシンで動かす必要がある（再測定が要る）。`ollama ps` の「100% GPU」表示は速度の保証にならない。
2. **カードは観測だけ、意味は用語集で渡す**（知識とデータの分離）。用語集の自動生成（アダプタが `src/lib/symptomVerdicts.js` の症状名・次の一手から作る）は**未実装**。
3. **質が足りないときの代替**（設計 §3）: 人間が症状カードを選んで Claude に貼る半自動運用。このコードの検査（カード・提案書・台帳）は、そのまま使える。
