# 共有部品が「あるのに使われない」— 重複実装の実戦KB

> 出典: `reply-copilot-openrouter-v2`（Chrome拡張）2026-09-01 実戦。
> ユーザー指摘:「同じパーツをちゃんと使えばならないはず。車輪の再発明もいいところです」

---

## この KB の要点（先に結論）

**ルールは既にあった。それでも守られなかった。**

キットには重複禁止が**3箇所**書いてある:
```
docs/ai-rules/01_CORE_RULES.md:11   同機能の重複実装をしない（既存部品を検索して再利用）
docs/ai-rules/03_REVIEW_CHECKLIST.md:6  [ ] 重複実装がない
docs/ai-rules/README.md:9           重複実装と手戻りを減らす
```
それでも同じ画面部品が3つ別々に実装されていた。
⟹ **文章をもう1行足しても解決しない。** 検査していない規範は守られない。

---

## 症状

同じ人物が、同じ画面で **2種類のアイコン**（写真と頭文字の四角）で表示される。
ユーザーが見て「コンポーネント化ができていない証拠では？」と指摘した。

実測した重複の規模:
```
                                    行数    共有描画部品を使うか
popup/features/shiori-expanded.js    760      ✗
popup/features/bookmarks.js        1,542      ✗
status.js                          1,618      ○   ← ここだけ
shared/conversation-render.js        186     （正本。185行で足りるはず）

同目的の関数が別名で重複:
  escapeHtml 29回 / 25回   ←→   esc() 75回（共有側と同名）
  formatDate  5回 /  4回   ←→   fmtTime（共有側）
```

---

## 原因

### ① 「共有部品はバグ修正が溜まる場所」だと認識されていなかった

共有部品を使わない画面は、**修正1つぶん永久に遅れ続ける**。
実例（同じ製品で実際に起きた）:

| 機能 | 共有部品を使う画面 | 使わない画面 |
|---|---|---|
| 同一人物の統合（改名しても1人として追う） | ○ | **✗** |
| 時系列の逆行検知 | ○ | **✗** |
| 発言日時が無いときの警告 | ○ | **✗** |

`shared/speaker-identity.js` は 2026-08-21 にユーザー指摘
「過去アカウント名変えたんだけどその扱いは？」を受けて作られた。
**その修正は1画面にしか入らず、ユーザーが日常的に開く画面では直っていなかった。**

⟹ 重複の本当の代償は「行数が多い」ことではなく、
　**「一度直したはずのバグが、別の画面では直っていない」**こと。

### ② 新機能も同じ経路で漏れる

同じ日に実装した新機能ボタンも、1画面にしか入れていなかった。
＝ ユーザーの画面には出ない。「実装したのに届いていない」の再生産。

---

## 直し方

### ✗ 効かなかった / やってはいけないと分かったこと

**✗ ルールを文章で足す**
　既に3箇所に書いてある。4箇所目を足しても同じ。

**✗「重複しているから」で機械的に統合する**
　★実測したら、**違いに正当な理由があるものが混ざっていた**:
```
拡大表示は「じっくり読み返す・検索する・保存する」画面なので全件描画する。
Ctrl+F・HTML保存・印刷はいずれも DOM に無いものを拾えないため、
仮想スクロールや遅延展開はこの画面の目的と正面から衝突する。
（過去に data-logs 二重持ちで 10MB になりページが落ちた実測あり）
```
　⟹ **描画戦略の違いは残す。統合するのは部品**（HTMLエスケープ・日時整形・アバター解決）。
　　混ぜると「統合したら遅くなった/落ちた」になる。

**✗ 症状の原因を、重複のせいだと決めつける**
　★今回**司令塔が実際に誤診した**。「共有部品を使っていないから
　アイコンが割れる」と説明したが、実コードを読むと違った。
　真因は「相手サービスが連続発言でアイコンを省くので、保存データが空」。
　**共有部品側も同じ制限を持っていたので、統合しても症状は残る**。
　⟹ **「重複を直す話」と「症状を直す話」は別物**。混ぜると
　　「統合したのに直っていない」になる。

### ○ 有効な順序

```
段0 数える（推測で統合を始めない）
    - shared/ の各部品を「誰が読み込んでいるか」を数える
    - 各画面が自前で持つ関数を突き合わせ、同目的のものを対応表にする
    - ★「重複しているが統合すべきでないもの」を理由つきで分ける
段1 症状を先に消す（統合とは切り離す）
    ★統合は影響が大きい。実害の解消を人質にしない
段2 検査を書く（ラチェット）。壊れた現物で赤くなることを先に確認する
段3 統合本体（最も危険なので最後）
```

---

## ★キットに足すべきは文章ではなく検査

`templates/diagnostics/` の11本を実測したところ、
**「同じものを2回書いていないか」を見る検査は1本も無い**:
```
grep -l "重複|duplicate|reuse|再利用" templates/diagnostics/*.mjs → 0件
```

⟹ `check-shared-parts-used.mjs`（実装済み・2026-09-01、`templates/diagnostics/run.mjs`に配線済み）。
既存の `check-instruments-reachable.mjs`（「計器は置いただけでは動かない」）と同じ型で:
- 冒頭に「★なぜ要るか」＝実損の記録
- 「★この検査が判定しないこと」を明記
- **ラチェット**（今の重複数が基準。増えたら赤・減らすのは自由）
- 3値の終了コード（ok / warn / unmeasured）

検出の手がかり（案）:
```
shared/ に公開部品があるのに、
同じ目的の関数を自前で持つファイルがある（escapeHtml ←→ esc 等、名前は揃わない）
／共有部品を1つも読み込まずに同じ種類の画面を描いている
```

★**実測結果（2026-09-07）**: 名前が違う同目的関数（少し違う実装）は`check-shared-parts-used.mjs`
　単体では拾えないと判明したため、別検査`check-near-duplicates.mjs`（行の正規化＋連続一致の
　塊検出）として新設した。`reply-copilot-openrouter-v2`で実測し、本KBが記録した実損
　（`popup/features/shiori-expanded.js`と`popup/features/bookmarks.js`の重複）が実際にクラスタ
　として検出されることを確認済み。詳細: `DESIGN-criterion7-near-duplicate-detection-2026-09-07.md`。
