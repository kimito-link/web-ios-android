# 別画面へUIを「鏡写し」にするときの掟

> ★これは**実装を配る文書ではない**。設計判断だけを配る。
> 実装（`mirrorSanitize.js` 等）はニコ生のDOM構造に最適化されており、
> ★他プロジェクトへそのまま持っていくと使えない。★持っていくのは【判断】の方。
>
> 出典: `tsuioku-no-kirameki.com`（Chrome拡張のpopup画面を、純Webページと
> 別窓に同じ見た目で出す機能）。★2026-05〜09の実装と実データで確定した知見。
> ★本文の事実は 2026-09-06 に実コードで裏取り済み。

---

## そもそも何の話か

**同じ画面を2つ以上の場所に出したい**とき、必ず起きる問題の話。

例:
- 拡張のpopupと、ログインなしで見られるWebページ
- アプリ本体と、OBS等に映すための別窓
- 管理画面と、共有用の公開ダッシュボード

★「同じものを出すだけ」に見えて、**素直に作ると必ず破綻する**。

---

## ★掟1: セクションを1個ずつ足していく作りは破綻する

★最初にやりがちで、★実際に破綻したのがこれ:

```
レーンの鏡を送る    → 別画面が描く
統計カードの鏡を送る → 別画面が描く
ランキングの鏡を送る → 別画面が描く   ← 1個ずつ足していく
```

★何が起きたか（実データ）:
> 数字カードは**17分前**で鮮度切れ・応援者ランキングは**未送信**・
> 人物レーンは**空**。★どれだけ足しても**永久に揃わない**。

★原因は単純で、**各セクションが別々のタイミングで送られる**から。
受け取る側から見ると「一部だけ新しい画面」になる。
★1個足すごとに「揃わない組み合わせ」が増える＝**足すほど悪化する**。

★ユーザーの「ひどい」という評価は、この構造が生んでいた。

---

## ★掟2: 送るときは【1回の束】にまとめ、世代番号を1つ持たせる

破綻を止めた形:

```
[送る側] 全セクションのスナップショットを1つの束にまとめる
             ↓ 束に世代番号(gen)を1つだけ付けて送る
[受け取る側] gen が前より新しいときだけ描く
```

これで **全部が同時・同一・鮮度は1つ**になる。★「揃わない」が構造的に消える。

### ★世代番号の落とし穴（実際に踏んだ）

★**画面を切り替えても gen を巻き戻してはいけない。**

```
配信Aを gen5 まで描いた
  → 配信Bに切り替え、gen を 1 に戻した
  → 受け取る側は「1 < 5 だから古い」と判定 ★配信Bが永久に描かれない
```

⟹ ★gen は**束の生涯を通じて単調増加**にする。
★「どの画面のデータか」の判定は **gen とは別の値**（画面ID）で行う。
★ここを混ぜると必ず事故る。

---

## ★掟3: HTMLを丸ごと運ぶなら、サニタイズは「自前の最小ホワイトリスト」で足りる

「画面のHTMLをそのまま送って貼る」方式を採るなら、消毒が要る。
★ただし**巨大なライブラリを入れる必要は無かった**（実測）。

★実際に必要だったのは、たったこれだけ:

| 扱い | 対象 | 理由 |
|---|---|---|
| ★**残す** | class 属性 | ★見た目はほぼ全部 class 駆動だった（inline style はほぼ0件） |
| ★**残す** | `href` の http/https のみ | ★全削除するとリンクが死ぬ。`javascript:` `data:` だけ落とす |
| **消す** | `style` / `on*` | XSS・CSP衝突 |
| **消す** | `[hidden]` 付き要素 | ★元画面で隠れていた物が、貼り先のCSSで**見えてしまう**事故 |
| **消す** | フレームワーク固有の属性 | 貼り先では意味を持たないノイズ |
| ★**書き換える** | SVG の `id` | ★同じ画面を複数並べると **id が衝突**して描画が壊れる。連番を付けて逃がす |

★**貼り先が元画面のCSSを持っていること**が前提。
　（この事例では、公開Web側のHTMLを拡張のpopupから丸ごと複製して作った）

---

## ★掟4: 「送り忘れ」は必ず起きる。だから機械に見張らせる

★新しいパネルを1つ増やすと、**手作業が5〜6箇所**必要になる:
```
(1)送る側でpublish (2)束に載せる (3)中継の組み立て
(4)受け取る側でpaint (5)貼り先のDOM (6)掃除の宣言
```

★どれか1つ忘れても **try/catch と no-op が握りつぶして、エラーが出ない**。
★実際にこれで、応援タイムライン・投げ一覧・配信採点が次々「出ないまま」になった。

⟹ ★**セクションの一覧表（レジストリ）を1つ作り、配線テストで照合する。**
```
一覧表に1行登録する → 配線が無ければ CI が赤
```
★登録漏れが**コンパイルは通るが動かない**状態を作れなくなる。
★この事例では 11セクションを登録し、16本の配線テストが見張っている。

---

## ★掟5: 一括方式と個別方式は、対立ではなく組み合わせ

★注意: 「丸ごと1枚方式に統一する」という設計判断が**一度は下されたが、そうならなかった**。

実際に出荷された形は**両方の組み合わせ**:
- ★**束（バンドル）** = 送る単位。全部を1 tick で同時に flush し、gen は1つ
- ★**セクション一覧** = 検証の単位。登録漏れを機械が捕まえるための表

⟹ ★「どちらか一方が正しい」ではない。
★**送るのは一括・数えるのは個別**が、実際に機能した形。

---

## ★やってはいけないこと（実際に失敗した順）

| ✗ | 理由 |
|---|---|
| ★セクションを1個ずつ足して揃うのを期待する | ★足すほど「揃わない組み合わせ」が増える |
| ★画面切替で世代番号を巻き戻す | ★新しい画面が永久に描かれない |
| ★消毒で `href` を全削除する | ★リンクが全部死ぬ。scheme だけ見れば足りる |
| ★消毒ライブラリを入れる | ★実測では自前の最小ホワイトリストで足りた |
| ★「登録したはず」を人間の注意力で担保する | ★握りつぶされてエラーが出ないので気づけない |

## ★この文書が扱わないこと（正直に）

- ★**実装は配らない**。消毒の許可タグ一覧は対象サイトのDOM構造に依存する
- ★**性能**は別問題。丸ごとHTMLを運ぶ方式は、一度「重い」という理由で
  別案が却下された経緯がある。★画面が大きい場合は実測してから選ぶこと
- ★リアルタイム性が要る場合の更新間隔・間引きはこの文書の範囲外
