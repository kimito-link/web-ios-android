## 3. ★往復で確定した掟（実測に裏打ちされたものだけ）

### ① Detect the SHAPE, not one function name

> 出どころ: `soushin-suggest.link/scripts/audit-sentinel-holes.ps1:156`

★**名前だけを見る検査は「名前を変えて黙らせる」ことを誘う＝有害。**

実損（`tsuioku`・2026-08-21）:
```
audit-gates.mjs が raw（コメント込み）を見ていた
  → ★コメントに「直し方」と書くだけで ✔ が取れた
  → 実コードだけを見るよう修正 →  5/13本 → 11/13本
  ＝ ★6本が偽の緑だった
```

★弱い印は、通す方向にも見落とす方向にも同じ壊れ方をする。

同じ日に逆方向でもう1件踏んだ（`tsuioku`・2026-08-21）:
```
自動記録した実測値2件の source が「括弧の有無」だけで手書きと区別されていた
  → ★読み手（AI）が「8件全部手書き」と読み違えた
  → source に [auto] を前置 → 見ればわかる印にした
  ＝ ★通す側と見落とす側、両方が「印が弱い」ことで起きる
```

### ② ★「exit 2 を持っているか」は正しさの保証にならない

> 出どころ: `soushin-suggest.link`（2026-08-21 実測）

```
壊れていた3本のうち ★2本は exit 2 を持っていた
  それでも「測れなかった」を製品の赤として報告していた
```

★所有の検査（grep）は**入口**でしかない。持っていることと守れていることは別。

### ③ ★毒が入ったことを確認してから、赤かどうかを見る

★**「変異させた」と「変異が適用された」は別物。**

実損（`tsuioku`・2026-08-21・2回）:
```
検知器を壊して赤を確認しようとしたら「✅ OK」
  → ★置換が空振りしていて、毒が1文字も入っていなかった
  → 毒が入っていないのだから当然緑。それを「合格」と読みかけた
```

対処: 毒を入れた後に **grep で毒の存在を確認**してから結果を読む。
`soushin` 側は `Invoke-WithPoison` ヘルパで**置換が0件なら即エラー**にした
（作った当日に、作者自身の間違った置換パターンを止めた実績あり）。

### ④ ★方向は数字から推測できない

> 出どころ: `tsuioku`（changelog 1,349版を機械抽出した実データ）

```
0.1.887   100% → 0%     ★改善（エラー率が消えた）
0.1.1298  2回 → 13回    ★改善（描画が動くようになった）
0.1.1102  3秒 → 12秒    ★改善（取りこぼしを無くした）
```

★「小さいほど良い」を既定にしていたら、この3件を**全部「退化」と誤判定**していた。
＝ ★**正しく直した人を止める**。検査への信頼は一度で消える。

→ 方向（`better: 'lower' | 'higher'`）は**指標ごとに宣言**する。

### ⑤ ★「測れなかった」を表す値を、判定式に素通しさせない

同じ穴が**向き違いで両方**出た:

| リポ | 穴 | 結果 |
|---|---|---|
| `soushin` | `-1`（測れなかった）が `-le 0` を通る | ★偽の**赤** |
| `tsuioku` | `null` が `Number()` で `0` になる | ★偽の**緑** |

★`tsuioku` は同じ穴を**1日に4回**踏んだ（毎回テストが先に発見）。
対処: `typeof v === 'number'` で明示的に弾く。判定より前に「測れたか」を確かめる。

### ⑥ ★レポートにする。一括強制のゲートにしない

★このキットで死んだ仕掛けは全部「一度に全部直せ」と迫るもの。

```
✗「書かないと赤」   → 強制すると【嘘の数字】が入る
✅「間違って書くと赤」 → 退化・未宣言だけ止める（ベースライン＋ラチェット）
```

★実例: `tsuioku` の登録制の台帳は**3ヶ月で登録1件のまま死んだ**。

### ⑦ ★ラチェットは「値が悪化した」より「走っていない」で死ぬ

★どちらも「退化」ではなく★**「検査が走っていなかった」**。
しかも入口ゲートだったので、★**赤の間プローブが1本も走っていなかった**。

→ ★**3値規約の外側に「そもそも走っていない」という4つ目の状態がある**（未解決）。

### ⑧ ★会議・AIに聞く前に、自分のリポの過去を検索する

> 出どころ: `tsuioku-no-kirameki.com`（2026-08-22・[`FROM-tsuioku-2026-08-22.md`](FROM-tsuioku-2026-08-22.md)）

★**会議は過去を知らない。** 地雷マップを渡さずに聞くと、踏んだ地雷をもう一度勧めてくる。

実損（`tsuioku`・2026-08-22）:
```

  → 案B: 「上限で切る」族（掟⑨に直結、3回踏んだ地雷）
```

対処: `git log --all --oneline --grep="<その手口>"` で先に自分の過去を検索してから聞く。

### ⑨ ★「上限で切る」は、たいてい「消えた」事故になる

> 出どころ: `tsuioku-no-kirameki.com`（2026-08-22・同日3回目の同型踏み）

★**「多すぎるから減らす」の前に、減らさずに済む方法を探す。**

```
存在を削る解（cap / 仮想化 / 遅延生成） → 後から届く更新を取りこぼす経路を作りやすい
見せ方を変える解（窓・スクロール）      → 存在は消えない
```

★付随する穴: `cap` に `Infinity` を渡すと、`Math.floor(Infinity / 2) = Infinity` で
フェイルセーフ（cap半減）が無力化する。上限を外すときは有限の実測値を渡す。

### ⑩ ★「入れました」の前に、依頼の言葉と成果物の表題を並べて読む

> 出どころ: `tsuioku-no-kirameki.com`（2026-08-22・AI自身の誤報告）

実損:
```
依頼: 「常にリアルタイムで診断する仕組みも欲しい」
入れた: 「診断が開かないときに測る手順」（壊れたときの最後の手段）
  → ★方向が違う。ユーザーが「これで合っていましたか？」と確認しなければ
     そのまま「入れました」で終わっていた
```

★特に「〜も欲しい」と追加で言われたものは、既にあるものの延長だと思い込みやすい。
→ 対処: 報告前に依頼文と成果物の表題を並べて読む。5秒で分かる。

### ⑪ ★計器は増やすほど良い、ではない

> 出どころ: `tsuioku-no-kirameki.com`（2026-08-22・計器100個の実績）

```
実績: 計器を2版続けて足したら止まる → 25版積んで症状の改善はゼロ
ユーザーの言葉: 「一体なんのため」
```

★**計器の価値は「真因に導いたか」だけで測る。数を誇らない。**
1本足すたびに判定し、導かなかったものは消す。「数えること」は「直すこと」ではない。
