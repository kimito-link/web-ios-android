## 0. ★何が汎用で、何がアプリごとか（これが設計の全部）

```
★汎用（どのアプリでも同じ）      … ①〜④の規約 と 判定のやり方
★アプリごと（必ずカスタムする）  … ★どの指標を、どちらが良いとして測るか
```

★**この線を引き間違えると死にます。**
「バンドルの大きさ」は多くのアプリで意味を持ちますが、
「コメントの遅れ」は特定のアプリだけのものです。
★**汎用にすべきは判定であって、指標ではありません。**


## 1. 何を解決するのか

★**バージョンを重ねても、良くなったと言い切れない**問題です。

追憶（`tsuioku-no-kirameki.com`）の changelog は **1,349版**ありましたが、
キーは `version / date / summary / items` の4つだけ。
★**文章しか無く、「軽くしました」と書いてあっても数字で証明できません。**

★さらに悪いのは、★**静かに元へ戻る**ことです。
1版ごとに少しずつ悪化すると、隣同士の差は小さいので誰も気づきません。

---

## 規約①　★方向は指標ごとに宣言する（数字から推測しない）

★**これが一番大事です。** 実データで設計がひっくり返りました。

changelog 1,349版から `before → after` を機械抽出した18件のうち3件:

```
100% → 0%     ★改善（エラー率が消えた）
2回 → 13回    ★改善（描画が動くようになった）
3秒 → 12秒    ★改善（間引きを緩めて取りこぼしを無くした）
```

★**「小さいほど良い」を既定にしていたら、この3件を全部「退化」と誤判定していました。**

これは単なる誤検知では済みません。
★**正しく直した人を「退化させた」と止めることになります。** 検査への信頼は一度で消えます。

```js
{ id: '...', better: 'lower' }   // 小さいほど良い
{ id: '...', better: 'higher' }  // ★大きいほど良い（0回＝動いていない、など）
```

★**数字の動きから向きを推測してはいけません。** 必ず宣言します。

---

## 規約②　★直前ではなく「過去最良」と比べる

```
1 → 2 → 3 → 4    隣同士は毎回「+1」なので小さく見える
                 ★過去最良(1)と比べれば 4 は明確に退化
```

★じわじわ悪化して元に戻るのを、直前比較では見逃します。

---

## 規約③　★記録し忘れは fail ではなく inconclusive（exit 2）

```
0 = 合格 / 1 = 測れた上での赤 / ★2 = 測れなかった
```

★**「記録していない」は【測っていない】であって【悪化した】ではありません。**

ここを赤にすると、記録が面倒なときに
★**"とりあえず数字を入れる" 動機**を作ります。★嘘の数字が入った台帳は、無い方がマシです。

---

## 規約④　★理由を書けば通す。ただし基準は最良のまま

意図した悪化は必ず起きます（機能を足せば増える）。
★そこで「数字を消す」ことを許すと、台帳の意味が消えます。
★**消させるのではなく、理由を書かせます。**

実装したら、この4つが成り立つことを**テストで固定**してください:

```
A note無しの退化        → 🔴
B note有りの退化        → ✅ 通る
★C 許した後にさらに悪化  → 🔴（★比較対象は許した値ではなく【過去最良】のまま）
D 空白だけのnote        → 🔴（黙らせられない）
```

★**C が要です。** 一度許しても★**悪い方が新しい基準になりません**＝ラチェットが緩みません。

★このキットで生き残った仕掛けは**全部この形**です（ベースライン＋ラチェット）。
既存の借金は許容し、★**新規だけ赤**にする。

## 2. ★実装するときの必須条件（先に決めておくこと）

### ① ★自動で測るのは「リポの中だけで完結する」指標だけ

| 自動にしてよい | ★自動にしてはいけない |
|---|---|
| ビルド成果物のサイズ | 実機の画面の部品数 |
| 検査の本数 | 起動してからの所要（端末で変わる） |
| 依存の数 | 通信の速さ |

★実機に依存する指標を自動化すると、★**測定条件が版ごとに違う数字**が
過去最良比較に載ります。★比べてはいけないものを比べることになります。

→ そういう指標は**手で書く**。★そのかわり `source`（どこで測ったか）を必須にする。

### ② ★収集（誰が値を書くか）はフックに置かない

★**生成物をフックで書くと、その追記は「いま送ろうとしている変更」に入りません。**
（追憶は同じ型を既に踏んでいます。生成物の再生成は `git add` の**後**でないと永久にズレる。）

★**契約はコマンド1本に閉じる**のが正解です:

```bash
<何か> record --metric <id> --value <n> --source "<どこで測ったか>"
```

★呼び手（フック / スキル / CI / 50年後の別の何か）は**必ず変わります**。
★変わってよいように、口だけ固定します。呼び手が死んでも口が残れば次を繋げます。

### ③ ★「測れなかった」を 0 として記録しない

```js
// ★悪い例（追憶はこの穴を1日に4回踏んだ）
value: Number(measured)     // ★null が 0 になる ＝ 測れていないのに「0」という実績が残る

// ★正しい
if (typeof v !== 'number' || !Number.isFinite(v)) return { verdict: 'inconclusive' };
```

## 2.5 ★台帳を入れても「測っていない」は起きる（実損 2026-08-22）

```
台帳を入れて8日後の実測(tsuioku-no-kirameki.com):
  診断の所要 … 最終記録が ★62版前
  パネル停止 … 最終記録が ★24版前
  他6種      … ★一度も記録が無い
  自動の2種  … 毎版(機械が書くので死なない)
⟹ ★10指標のうち【自動の2つしか動いていなかった】。
  その間に診断の所要は 29,303ms → 19ms と ★1,500倍 動いたのに記録は0件。
```

★台帳は「改善している」と表示しながら、★**ほとんど何も測っていなかった**。
★これは「オプトインの台帳は死ぬ」の再来（同リポの別の登録簿は3ヶ月で登録1件のまま死んだ）。

### ⟹ 対策: `lib/improvement-staleness.mjs`（キット同梱・依存ゼロ）

```
改善記録の鮮度: 測れている 6 / 10 種
  🟡 1種が放置されています(測れるのに測っていない): パネルが止まる時間(24版前)
  ⚪ 4種は一度も記録がありません(★測る手段が無いだけかもしれません)
```

★**書くことは強制しない**（規約③と同じ理由。強制すると「とりあえず埋める」で嘘の数字が入る）。
★**数を見せるだけ**にして、忘れたことを忘れられないようにする。

★**「一度も無い」と「測れるのに測っていない」を分ける**。
前者は測る手段が無いだけかもしれないので、混ぜると優先順位が付けられない。

★`check-improvement.mjs --selftest` が★**放置を検知できるか**まで自分で試す
（毒を入れて「stale と言えなくなる」ことを確認済み・2026-08-22）。

## 3. ★台帳を死なせない工夫

```
✗「書かないと赤」   → 強制すると【嘘の数字】が入る
✅「間違って書くと赤」 → 退化・未宣言だけ止める
```

★追憶では**登録制の台帳が3ヶ月で登録1件のまま死んだ**実績があります
（オプトインの台帳は必ず死ぬ）。

★**書くこと自体は強制しない。** そのかわり:

```
★いまの版が台帳に無ければ inconclusive（exit 2）で鳴らし続ける
  → 忘れたことを【忘れられない】
  → ★fail にしないので、嘘の数字を入れる動機は作らない
```

## 4. ★申請・審査に使える形にしておく

指標と実測値が揃うと、★**「何を測って、どう良くなったか」を実測値だけで1枚**にできます。

```

✅ バンドルの大きさ:   2400KB → 1360KB 改善
✅ パネルが止まる時間: 1373ms → 106ms 改善
```

★**体感や願望を書かない**（`source` が無い数字は載せない）ので、そのまま出せます。

```

   → 実測(2026-08-22): 台帳22エントリ・[auto]印14件
     0.1.1471〜1477 は★全版記録（台帳は 0.1.1470 で作られた）

     `🟡 いまの版 0.1.1477 の実測値が台帳にありません` / ★exit 2
```

### ★配るときに塞いだ穴（移植で見つかった・実測で確認）

★収穫元 tsuioku の selftest は**アプリの指標名**（`diag-ms` 等）を直書きしていた。
キットは指標テーブルを★空で配るので、そのまま持ってくると:

```
未宣言の指標 → detectRegressions() は判定せず [] を返す
  → 「退化なし＝合格」と読める
  → ★真実は「一度も判定していない」  ＝ 掟⑤ と同型の偽の緑
実測(2026-08-22): 未宣言の 5→900（明らかな退化）で★検知0件
```

→ ★**判定は指標テーブルを引数で受け取る**形にし、
★**selftest は自前の表を注入して**自分を試す（アプリの表が空でも検知器の生死を判定できる）。

### ★あわせて配った「4つ目の状態」

`check-instrument-ran.mjs` … ★**そもそも走っていない**を検出する。
台帳の門番は「記録が無い」は言えるが、★門番自体が呼ばれなければ何も起きない

★走らなかった検査は何も出力しない＝内側からは観測できないので、
★緑のときだけ記録を残し、常に前へ進むもの（コミット）との距離で測る。
