# 常にリアルタイムで診断する ＋ コピペ1回で不具合を伝える

> ★これが「けんこう診断」の**本体**。
> 壊れて開かないときの最後の手段は [`MEASURE-WHEN-DIAGNOSTICS-WONT-OPEN.md`](MEASURE-WHEN-DIAGNOSTICS-WONT-OPEN.md)。

---

## 0. ★2つで1組（片方だけでは機能しない）

```
① 常時リアルタイム診断 … アプリが【自分の状態を測り続ける】
② コピペ1回の共有      … その結果を【1回のコピーで開発者に渡せる】
```

★**①だけだと「画面を見ないと分からない」**＝ユーザーがスクショを何枚も撮ることになる。
★**②だけだと「そのとき何が起きていたか」が残らない**＝再現待ちになる。

★実績（`tsuioku-no-kirameki.com`）: この2つが揃ってから、
★**「診断817秒→0.005秒」のような原因特定が、ユーザーの操作1回で回るようになった。**

---

## ① 常にリアルタイムで診断する

### 骨格（そのまま移植できる形）

```js
/**
 * 自動更新:
 *   - setInterval 2秒
 *   - ★document.hidden で停止（電池・CPUを食わない）
 *   - ★書き手が変えた瞬間だけ増分更新（storage.onChanged 等）
 */
```

★3つとも要る。**2秒間隔だけを真似すると、裏で回り続けてアプリを重くする。**

### ★読む頻度は「書き手の更新間隔」から決める（ここが50年の肝）

★**やってはいけない決め方**:

```
✗ 鮮度要求で決める … 主観（「1秒でも困る」vs「10秒平気」）＝基準にならない
✗ 実測所要で決める … 競合で 1ms↔217ms と揺れる＝追従すると振動してデバッグ不能
```

★**唯一使える軸**:

```
✅ 書き手の更新間隔 … コードにハードコードされた【不変の事実】
```

★実損（追憶）: この基準が無かったため、★**人の判断で3回引っ越しが起き、根拠がどこにも残らなかった**。
★次に計器を足す人が、また一から考えることになる ＝ これが「50年後つらい」の正体。

→ ★**「どの計器をどの頻度で読むか」を宣言する1ファイル**を持つこと。
　 実物: `src/lib/statusReadPolicy.js`（純関数・判定だけ）。

### ★計器がアプリを殺さないための鉄則

```
★計器を1本足したら、必ず【更新にかかる時間】を測る
★既存のバッチに相乗りさせる（読み取りを1本増やさない）
```

★実損: 読み取りを1本足しただけで**診断が817秒**かかった（体感が完全に壊れた）。

### ★「取り込み中」は載せない

★ユーザーは**進捗を見に来ている**。読み込み途中の値を「現在の状態」として出すと、
★正常なのに警告が居座る（累積値を現在値として出す事故）。

## ② コピペ1回で不具合を伝える

### 何を出すか

```
1. ★いつの値か（何秒前か）           ← これが無い数字は読めない
2. 何が起きているか（症状の言葉で）
3. ★判定（🟢正常 / 🟡注意 / 🔴異常 / ⚪測れていない）
4. ★次の一手（読んだ人が何をすればいいか）
5. 生データ（JSON・AIが読む用）
```

### ★4値で答える（3値exit と同じ思想）

```
🟢 正常
🟡 注意
🔴 異常
⚪ ★測れていない ← これを「正常」に混ぜない
```

★「0件」は「異常なし」ではなく「まだ測っていない」かもしれない。
★詳しくは [`HANDOFF-new-app.md`](HANDOFF-new-app.md)。

### ★症状の言葉で並べる

★開発者の言葉（fail-open / race / provisional）で並べると、
★**ユーザーは自分の症状がどれか分からない**。

```
✗ 「laneRenderProbe が未完走」
✅ 「パネルが黒い・重い」の枠に入れる
```

★実損: ユーザーに**10回言われて**やっと直した（症状の言葉で枠に分ける）。

### ★画面にしか出さない情報は「無いのと同じ」

★コピーに載らない情報は、報告に乗らない＝存在しないのと同じ。
★**判定は、症状が出ている当の画面にも出す**（異常時のみ・1行目に次の一手）。

---

## ③ ★この2つを腐らせない仕掛け

```
★計器の価値は「真因に導いたか」だけで測る
   → 導かなかった計器は、足しても意味がない（数を誇らない）

★計器を2版続けて足したら止まる
   → 実績: 25版積んで症状の改善ゼロ。「数えること」は「直すこと」ではない

★出力に出たか必ず確認する
   → 「計器を書いた＝測れている」ではない。出荷物を grep して実在を見る
```

---

## ④ 実装の順番（新しいアプリで）

```
1. ★まず「何が壊れたら困るか」を1つ決める（全部は測らない）
2. その1つを測る計器を1本だけ書く
3. ★コピーに載せる（画面だけに出さない）
4. ★実際に1回、その計器で原因を特定してみる
5. 導けたら次の1本へ。導けなかったら【消す】
```

★**最初から100個作らない。** 追憶は100個まで増やしたが、
★真因に導いたのはごく一部だった。

## 付録：実物の場所（動いているコード）

```
tsuioku-no-kirameki.com/
  src/extension/status-entry.js   … 自動更新2秒 + hidden停止 + 増分更新
  src/lib/statusReadPolicy.js     … ★読む頻度の正本（書き手の間隔から導く）
  src/lib/aiShareFullText.js      … ★コピペ1回の共有テキスト組み立て
  src/lib/healthCellGroups.js     … 症状の言葉でセルを枠に分ける
  src/lib/diagnosisRegistry.js    … セルの登録（新セルは登録必須）
```

★キットにコードは同梱していない（アプリごとに測る対象が違うため）。
★**移植するのは「骨格と鉄則」**であって、指標そのものではない。
