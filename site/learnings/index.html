🔐 認証つきアプリの §4.8（Sign in with Apple）— 第三者ログインの種類で対応が変わる

§4.8: 第三者/ソーシャルログイン（Google・X(Twitter)・Facebook 等）で主アカウントを作る/認証するアプリは、 同等の選択肢として Sign in with Apple(SIWA) を併設しなければならない。server.url 連動型でも ログイン画面は本番Webそのものなので、アプリ内に出るログインボタンが §4.8 の対象になる。

分岐：Email/PW があるか、ソーシャル専用か

  • A. Email/PW + ソーシャル（例: Gmail 併用） → iOS だけソーシャルボタンを隠す。 carve-out #1「自社アカウント基盤のみ」が成立し §4.8 が発火しない。Email/PW で入れるので機能は無傷。 実証: partnership_program_website（applyIOSGoogleHide() + CSS + MutationObserver の3層）。
  • B. ソーシャル専用（例: X 専用ログイン） → 隠すとログイン手段がゼロになり A は使えない。 よって SIWA を併設(Strategy A)して正面突破する。app.config.json に appleSiwaServiceId を予約 → Clerk→Apple Developer 設定後 siwaEnabled:true。

もう一つの壁：ソーシャル OAuth は WebView で拒否される

Google OAuth は埋め込み WebView を UA で検出して拒否（403 disallowed_useragent）。 X(Twitter) OAuth も同方針。Bパターンは SIWA 併設に加え、必要なら @capacitor/browser で OAuth を SFSafariViewController に逃がす。

Clerk はプロバイダのプラットフォーム別出し分けが無い（instance 単位でグローバル）。 iOS で隠すのは UI レイヤーのみ（上記3層）。
allowNavigation の落とし穴: 連動型で本番ドメインしか許可しないと OAuth リダイレクト先 （x.com / *.twitter.com / *.clerk.com / *.clerk.accounts.dev）が 遮断されアプリ内ログインが必ず失敗する。capacitor.config の server.allowNavigation に必ず足す。
審査用デモアカウント(§5.1.1)必須: ログインアプリは審査員が入れないと即却下。2FA は無効化して渡す。

出典: _docs/apple-reject-knowledge-base.md §4.8（リバースハック実通過の返信文つき）／ kimito.link（X専用＝Bパターンの実適用）。

▶ Android（Google Play）

人間が触る画面

  • Play Console でアプリ枠作成 → playAppId + assetlinks 用 SHA-256 を AI に渡す
  • 内部テスト or 製品版で AAB ドロップ → 審査に送信ボタン（押すまで審査始まらない）
  • 申告は順番固定＋各画面で保存/送信（データの安全性・広告 ID がハマりどころ）
  • 製品版本番: ダッシュボード 5/5 → 公開の概要で N 件まとめて送信（RH 実証: 9件）
  • 新規個人アカウント: クローズドテスト 12人×14日 → 本番アクセス申請が別途必要な場合あり
  • GitHub Secrets 3個: keystore + SA JSON

CI / スクリプトで自動

  • TWA bundleRelease → play-publish.mjs
  • ストア素材: generate-play-assets.mjs / listing: play-set-listing.mjs
  • 製品版 promote: play-setup-production.mjs / play-submit-review.mjs
  • 再提出時は playVersionCode を必ず increment（例: 6→7）
  • 複数ブランド: app.config.reverse-hack.json + パッケージ別 assetlinks fingerprint

📷 画面付き手順 → iOS 追体験 ／ Play 追体験

製品版だけの罠（2026-07 実証）: 内部テストには無いが、製品版（一般公開）を出すときは 「配信国/地域」の選択が必須。未選択だと赤字で「国または地域が選択されていません」と出て 保存できない。「国/地域」タブで国（例:日本）を追加すればOK。
広告IDの申告は「広告」欄とは別ダイアログ: 11項目で「広告は含まれていません」を選んでいても、 審査に送る直前に別の確認ダイアログ「広告 IDの申告が不完全です」が出る。広告SDKを使わない 殻アプリ（Capacitor/TWA）は「いいえ」で通過。
一覧のアイコンが変わらなくても焦らない: ストア一覧に出るアイコンは最後に配信済みの バージョンのキャッシュ。新しいアイコンを入れた審査待ちビルドを出しても、承認・配信される まで一覧は古いアイコンのまま表示される（審査待ちビルドの中身は新アイコンで正しく入っている）。

🤖 AIに「提出できません」と3回言われた話

Chrome 拡張の申請をAIに頼んだら、「ダッシュボードへのログインと提出ボタンは代行できません」 と断られました。過去に何度もやってもらっていたのに、です。3回言われて、ようやく原因が分かりました。

AIは2つの別々の事実を混同していました。

  • ✅ 本当: Chrome ウェブストアの管理画面は、ブラウザ自動操作が全面的にブロックされている （Chrome のポリシー。スクリーンショットすら撮れない）
  • ✅ 本当: でも公式の申請APIがある。API経由なら審査送信まで全自動でできる
  • ✗ 誤り: 前者から「だから提出できない」と結論すること

「画面を操作できない」と「提出できない」は別の話でした。 実際にはコマンド1本（npm run publish:cws）で審査キューに入ります。

ややこしいのは、ストアごとに「自動化の境界」が逆なこと

ファイル送信掲載文の入力審査に送る
Chrome自動手動自動
Google Play自動自動手動

Play は掲載文まで自動で入れられるのに、最後の「審査に送信」だけは人間がボタンを押します。 Chrome はその逆で、審査送信は自動なのに掲載文の貼り替えだけ手動です。 「片方でこうだったから、もう片方も同じはず」が通じません。

  • 教訓①: 「できません」と言う前に、まず自動化スクリプトの有無を確認する （ls scripts/ | grep -i publish の1行で済む）
  • 教訓②: 制約は「何が」できないのかを正確に切り分ける。 「ブラウザ操作の不可」を「作業全体の不可」に広げない
  • 教訓③: 同じ説明を人間が2回以上させられたら、それはドキュメントの不備。 このページと _docs/chrome-web-store-submission-playbook.md はその結果です

🤝 別プロジェクトのAIが、この心臓部（CLAUDE.md）を実測で正し合った話

このキットの CLAUDE.md は「全プロジェクトが従う設計の心臓部」を掲げています。 では実際に、別のアプリを作業中のAIセッションが知見をここへ書き戻しに来たとき、何が起きるのか。 2026-09-01、malwarecheck.site を担当していた別セッションが、IAP（アプリ内課金）実装で得た 知見をこの CLAUDE.md に書き戻しに来ました。

  • ①知見の提供: 「IAPの実装の型がキットに無い」ことに気づき、実装済みの2プロジェクト （PHP原型・Next.js移植）へのパスを添えて追記案を用意した。ただしmainへは直接コミットせず、 担当セッションに委ねた（このリポは別セッションが作業中の可能性があるため）
  • ②受け取り側の裏取り: このリポを担当していたセッションが、提案された8個のファイルパスを 全て実在確認し、参照コードが実際に公式ライブラリを使っているかまでコードで確認してからコミットした
  • ③2回目の追記とその中の誤り: 同じセッションが「越境時の作法」を追記した際、 「CLAUDE.mdへの追記は自動でハブ（kimito-skill.link/hub/）に出る」と実コードを確認せずに書いてしまった
  • ④実測での訂正: 受け取り側が generate-hub-dashboard.mjs を実際に読み、 ハブは ai-hub/index.json 経由の別経路でCLAUDE.mdの中身は読んでいないこと、 Web公開の実体は「このリポ自体がGitHub上でpublicだから」だと突き止めて訂正した
  • ⑤本人による受容: 提供側は「実在確認済みのことだけ書け、と自分で追記したその隣で、 自分自身が推測を書いていた」と認め、訂正を歓迎した

皮肉なのは、③で書かれかけた誤りが、まさに①②で実践されていた原則 （実在確認してから通す・自分の持ち場のコードは自分で検証する）を、 提供側自身が一瞬破っていた、という点です。それを正せたのは、受け取り側が 「越境してきた知見でも無条件で採用せず、自分のコードで裏取りしてから通す」 という一手間を挟んだからでした。

  • 教訓①: 知見は「持っている側」と「検証できる側」が別人であることが多い。 越境してきた知見を無条件で信じず、受け取った側の持ち場で裏取りしてから通す
  • 教訓②: 「委ねる」側が git add・commit までせず差分だけ残して手を止めたのが機能条件。 押し切ってpushしていたら、誤りを含んだまま心臓部に残っていた
  • 教訓③: この一連のやり取り自体が「越境時の作法」として CLAUDE.md に明文化され、 次に別プロジェクトから来るAIセッションは同じつまずきを繰り返さない

  • 提出リトライループが重複 → 1本に統合（retry-ios-submit.mjs）

🌀 「AIと一緒に迷路を歩いている感」という指摘は、たぶん正しい

SNSで見かけた投稿（@fre2dm さんの発信）の要旨は、 AIにコードを直してもらうたびに別の場所が動かなくなり、それをまたAIに聞いて直す というループが続く、というものでした。その状態を指して 「AIと一緒に迷路を歩いてる感」と表現されていました。

これを他人事として読めませんでした。このキット自身が、直前の2つのカード （サムネイル・ID・アイコン・名前の話／ヘッダー・フッターの話）で、まさにこの型を 踏んでいます。1箇所直したつもりが、別のプロジェクト・別のページで同じ不具合が 直っていない。指摘されてから気づく。直す。また別の場所で同じ形が見つかる。

  • 教訓①: 「迷路化」の正体は、直した知見が次の場所へ届いていないこと。 1回の修正が1箇所にしか効かない設計だと、プロジェクトが増えるほど迷路が広がる
  • 教訓②: このキットがai-hub/find・templates/への格上げ・ 知見の書き戻しにこだわるのは、この迷路そのものを狭くするため。 「同じ調査をもう一度AIにやらせない」が目的であって、AIの性能の話ではない
  • 教訓③: 迷路の中を歩いている自覚がないと抜け出せない。「また直った」で 満足せず、「なぜ前回は防げなかったか」まで戻って考えるのが、この一連の 修正で実際に効いた動き方だった

🔍 「直したのに変わらない」を3回やった話

AIに調査させると、コードを読んで「たぶんここが原因」と推論します。 それらしい答えが返るので、つい信じて修正に進みます。 でも読んだファイルが、実際には使われていないことがあります。

  • 「この定数が設定に入っているはず」→ 受け皿はあるが、渡している箇所が0件。表示用に返るだけだった
  • 「この軽量版が使われるはず」→ 機能フラグはONでも、その分岐に到達していなかった
  • 「AIの出力が悪い」→ AIは別の文を返していて、後処理が定型文に差し替えていた

3回とも、コードは十分に読み込んだ上で外しています。 解決したのは、実際に送信されている中身を1回だけ丸ごと覗いたときでした。 想像していた構造と全く違い、指示が16,956文字あって肝心の入力データは末尾にありました。

  • 教訓①: 目印の文字列を1つ入れて、実行時に届いているか見る。これだけで空振り3回が消える
  • 教訓②: 入力と最終出力を並べる。違っていれば、間の後処理が原因
  • 教訓③: 同じ定数が2箇所に複製されていないかを grep で確認する
  • ✗ 効かなかった: 上位モデルへの差し替え。4種のAIで実測したが有意差なし。しかも別ベンダーの3つが一字一句同じ答えを返した（＝原因は自分のコード側だった）

「性能の高いものに変えれば直る」は、原因を特定する前にやると費用だけ増えます。 詳細は _docs/runtime-truth-verification-knowledge-base.md に残しました。

🧩 「サムネイル・ID・アイコン・名前」を、プロジェクトごとに別の形で作っていた話

姉妹プロジェクトから「AIが実装前に、既にある機能を知らずに新規実装しようとする型の失敗が 複数のプロジェクトで見つかった」という報告が届きました。ルールとして重複実装を避けることは 3箇所にすでに書いてあり、文章としては十分でした。それでも起きていました。

返信を書き終えた直後、まさに同じことを自分がやっていたと分かりました。 新しい機能（複数のチャット相手をひとつの案件としてまとめるAI秘書）に、 メッセージの送信者を表示するタイムラインを新しく作ったのですが、 「役割名＋名前」のテキストだけで済ませていました。

一方、姉妹プロジェクトには既に「人物」の表し方の正本がありました。 アイコン画像 or 名前から決まる安定した色つきの頭文字、IDは改名しても同一人物と分かる鍵として保持する、 という形です。しかもそのコードには 「2026-08-21実機で『サムネイルが出ない』として発覚した」という実際の事故の記録まで コメントに残っていました。それを読まずに、劣化版を新しく書いてしまったのです。

  • 教訓①: 「重複実装をしない」という文章のルールは、実装前に読みに行かなければ効かない。 ルールが良い場所に書いてあることと、それを使うことは別問題
  • 教訓②: 「サムネイル・ID・アイコン・名前」のように複数の値をひとまとめにして扱う概念ほど、 プロジェクトをまたいで別の形を作りやすい。人間なら普通しない
  • 教訓③: 事故の記録はコードコメントに書くと、次に読む人（AIも）が実装の瞬間に必ず目にする。 別文書に置くより効く場面がある
  • ✗ 効かなかった: ルール文を4箇所目に増やすこと。3箇所で足りなかったものが4箇所で足りるとは限らない。 直したのはルールの数ではなく、実装前に姉妹プロジェクトを見に行く手順そのもの

この件は横断の索引（ai-hub/index.json）にも登録し、次に別プロジェクトで 同じ判断を迫られたときにfind --tag duplicationで見つかるようにしました。 正本はこのキットの_docs/に残し、索引には要約だけを置く、という置き場所の使い分けも、 「正本を2つ作らない」という同じ教訓の実践です。

🧱 「このキット自身」に実装があるだけでは、他のプロジェクトからは見えなかった話

上のカードのすぐ後、実際のスクリーンショットを見せられました。別プロジェクトの LP（複数ページの静的サイト）で、ページごとにヘッダー・フッターがバラバラ になっていました。共通のナビゲーションが無く、フッターの中身もページによって 文言が違います。

調べると、このキット自身のsite/（今あなたが読んでいるこのサイト）には、 ヘッダー・フッターを1箇所で管理する実装が既にありました。 24ページ以上に生HTMLをコピペしていたのを2026-08-22に廃止し、JSが実行時に 差し込む方式に直した実績があります。それなのに、この実装はsite/の 中だけに閉じていて、templates/（他プロジェクトが金型として使う場所） へは一度も格上げされていませんでした。

「このキットは、全プロジェクトが従う設計の心臓部であるべき」という指摘を受けて、 site/scripts/site-chrome.jsからキット固有の値（ナビ項目・ブランド名）を 抜き、templates/web/site-chrome/として一般化しました。複数ページの 静的サイトを新規に作るときは、この金型をコピーしてブランド情報だけ書き換えれば、 最初からヘッダー・フッターが1箇所管理になります。

  • 教訓①: 「自分のプロジェクトで実装した」と「他のプロジェクトが使える」は別のこと。 templates/へ格上げして初めて、キットを使う全プロジェクトから見える
  • 教訓②: 心臓部であるべき場所ほど、自分自身がその原則を体現できているかを疑う。 「ルールを他プロジェクトに求める」前に「自分は金型を配布物にしているか」を確認する
  • 教訓③: これは前のカードの「人物表示」の話と同じ根。対象がヘッダー・フッターか アイコンかが違うだけで、「共有すべき部品を個別に作ってしまう」型は繰り返し起きる

🤖 AIの中に、係の人を3人おきました

  • けんさ係できあがったものを、作った本人じゃない目でチェックする。 テストの点数じゃなく「ほんとうに動いた証拠」を見る係。（reality-checker）
  • しんさの先生お店（App Store / Google Play）に出す前に、 「前にこの理由で落ちた」ノートと見くらべてくれる係。（store-guard）
  • きろく係今日つまずいたことをノートに書いて、 次から同じ穴に落ちないようにする係。（harvester）

📟 「見てきて」と頼まなくて済むようにした話

不具合を直すとき、いちばん時間を食うのは修正そのものではありません。 AIが「実機でどうなっているか分からない」ので、毎回あなたに見てもらう往復です。 「開いて、そこを押して、どう見えるか教えてください」——これが1日に何度も起きます。

直し方は、アプリ自身に自分の状態を数字で申告させることでした。 画面を見なくても、コマンド1回で今の状態が1枚のテキストで出てきます。

  • 数える場所を段ごとに置く: 受け取ったN件 → 保存したN件 → 表示したN件。減った段が壊れている場所
  • 遅さは実測ミリ秒で持つ（「重い気がする」ではなく、実際に測った秒数で言う）
  • 出力はコピペ1枚にまとめる。AIはそれを読むだけで切り分けられる

これで、調査の往復から人が外れました。 「目視をお願いして説明を待つ」が「コマンド1回・数秒」になっています。

  • 教訓①: 0件は「起きなかった」ではなく「測っていない」かもしれない。両者は必ず区別する
  • 教訓②: 合格・不合格の2つでは足りない。「測れなかった」を足して3つにする。でないと、何も測っていないのに合格と出る
  • 教訓③: 検査自身をわざと壊して、ちゃんと不合格になるか確かめる。壊れた検査は、静かに全部通します
  • ✗ 効かなかった: 計器を増やすこと自体。読み取りを増やしすぎて診断が817秒かかり、アプリを重くしました（まとめて読む形に直して5ミリ秒）。計器が製品を遅くしたら本末転倒です

考え方の全体はキットの説明書（AIが読む用）に入っています。 新しいアプリを作るときは、作り始める前に読ませてください。 後から計器を足すのは、作りながら足すより何倍も高くつきます。
