# App プレビュー動画を作って差し替える

> 実リポ: `C:\Users\info\OneDrive\デスクトップ\Resilio\github\kimitolink-linktree`
> スクリプト一式: `scripts/app/` （下記はすべて実在・動作確認済み）

## 0. ★最初に読む: なぜ却下されるのか

Guideline **2.3.4** の原文（developer.apple.com/app-store/review/guidelines/）:

> previews may only use **video screen captures of the app itself**.
> You can add **narration and video or textual overlays** to help explain
> anything that isn't clear from the video alone.

★**映像の土台はアプリの画面収録だけ**。ナレーションと字幕は**明示的に許可**されている。

| | 可否 |
|---|---|
| アプリの画面収録 | ✅ これだけが土台になれる |
| ナレーション音声 | ✅ 公式が録音機材の品質にまで言及して推奨 |
| テキスト/映像オーバーレイ | ✅ 原文に明記（"video or textual overlays"） |
| キャラ・図解が**画面を占める** | ❌ **2026-10-20 に実際に却下された** |
| 人物の手・実写 | ❌ "Don't film people interacting with a device" |

### ★実例（判断に迷ったらこれ）

**PayPay** のプレビューは、アプリ画面を**中央に縮小**し、下に**赤い帯＋大きなテロップ**（画面の約2割）。
⟹ 画面の隅にキャラを重ねるのは、これより控えめ＝通る見込みが高い。

★App Store の poster 画像は **WebFetch では取れない**（HTML をテキスト化するため）。
ブラウザで `document.querySelectorAll('video')` の `poster` を読み、その URL を直接開く。

## 1. 作る（スクリプトは実在する。ゼロから書かない）

```bash
node scripts/app/make-preview-voice.mjs   # VOICEVOX → narration.wav + timeline.json
node scripts/app/make-preview-chars.mjs   # 顔パーツを合成（任意）
node scripts/app/make-preview-se.mjs      # 効果音を自前生成（任意）
node scripts/app/mix-preview-audio.mjs    # 声+BGM+SE をダッキングして1本に
node scripts/app/record-app-preview.mjs   # 実画面を録画 → 音声を mux
```

### ★WebView 薄殻なら「ブラウザ録画＝実機画面」

`capacitor.config.ts` が `server.url: 'https://...'` の薄殻アプリは、
同じ URL を同じ画面サイズでブラウザに出せば**実機と同一の画面**になる。
撮影対象は**実在する公開ページ**にする（モックは 2.3.3 で却下された実績あり）。

### ★台本の歯止め（これを外すと別の却下を呼ぶ）

1. 全セリフの主張は**同じカットの画面録画で確認できること**に限る
2. 数の主張ゼロ / 3. 未来を約束しない / 4. 他社名・比較を出さない
5. 1行 **40字以内** / 6. 同じ話者を連続させない

`preview-script.mjs` の `validateLines()` が機械チェックする。**音声生成の前に必ず通す**。

## 2. ★★ここで溶かす（実測した罠 6 つ）

| 症状 | 真因 | 直し方 |
|---|---|---|
| 冒頭が灰色のプレースホルダ | 録画は `newContext` の時点で始まる | 準備時間を測り ffmpeg の `-ss` で捨てる |
| 字幕が録画で**下端から切れる** | ★Playwright の `recordVideo` は `position:fixed` の下端を正しく描かない（ページ上では `bottom=896` で収まっているのに欠ける） | `bottom:56px` へ浮かせる |
| 1ビート目なのに最下部が映る | 火入れスクロール後にページ高が伸びて位置がずれる | `scrollY<=2` を**待ってから**本編 |
| 画面が上下に跳ねる | 見せたい順に並べたら位置が前後した | **ページの上から下**へ並べ替え |
| 尺が30秒を超える | 見積りで台本を書いた | ★**音声を先に生成して実測**してから削る |
| ロゴが別ブランドだった | ファイル名で選んだ | ★**中身を見てから選ぶ**（`logo-text.png` が別社のロゴだった） |

★`scrollIntoViewIfNeeded()` と `behavior:"smooth"` を併用しない（瞬間移動してから滑る）。

## 3. ★★差し替え（ここが一番詰まる）

### 画面の場所（迷子になる）

```
バージョンページ → 「ヘッダと検索結果 ∨」をクリック
  → ドロップダウンから「アプリプレビューとスクリーンショット」を選ぶ
  → 「メディアマネージャですべてのサイズを表示」
```

★バージョンページを素直に見ても**プレビュー欄は出てこない**。
「ヘッダと検索結果」は `tablist` で、そこに隠れている。

### ★順序（間違えると審査に出せなくなる）

```
1. 新しい動画を入れる
2. ★それから古い動画を消す
```

先に消すと「プレビュー0本」の状態が生まれる。

★**古い素材は必ず全サイズで消す**。v1.0.8 の前例で、作り直したのに ASC に
古い素材が残っていて**同じ理由で再却下**された。

### ★Apple 公式の技術仕様

developer.apple.com/help/app-store-connect/reference/app-preview-specifications/

| | |
|---|---|
| 解像度 | 886 x 1920（iPhone 大型・縦） |
| **Target bit rate** | **10-12 Mbps** ★低いと保存に失敗する疑い |
| プロファイル | up to High Profile **Level 4.0** |
| フレームレート | 最大 30fps |
| 音声 | **256kbps AAC** / ステレオ / 44.1k or 48k |
| 長さ | **15〜30秒** |
| 最大サイズ | 500MB |
| ★**処理時間** | ★**アップロード後 最大24時間** |

```bash
ffmpeg -i IN.mp4 -vf "setsar=1" \
  -c:v libx264 -profile:v high -level 4.0 -pix_fmt yuv420p -r 30 \
  -b:v 11M -maxrate 12M -bufsize 20M \
  -c:a aac -b:a 256k -ar 44100 -ac 2 \
  -movflags +faststart -y OUT.mp4
```

### ★★詰まったときの判断（2026-10-21 に溶かした箇所）

**「ファイルを保存できませんでした」が出る**

- ★ビットレートが低いと出る疑いが濃い（1.27Mbps で3回失敗 → 2.11Mbps でエラーが消えた）
- ただし**確定ではない**。フォーラムには 38Mbps が通り 10Mbps が詰まった報告もある
- ⟹ まず公式の 10-12Mbps で作り直す

**グレーの雲アイコンのまま止まる**

- ★**失敗と決めつけない。公式が「最大24時間」と書いている**
- 消して上げ直すと処理がやり直しになるだけ。**待つ**
- ★同じ枠に何度も上げない（処理待ちが積み上がって状況が読めなくなる）
- ★**2026-10-21 の実測では 5〜10分でサムネイルに変わった**。雲 → 再生ボタン付きサムネが成功の印

#### ★「5／10」の数字は処理完了を意味しない（2026-10-21 に誤読した）

枠の `アプリスクリーンショット数：5／10` は**アップロード済みの件数**であって、
**サムネイルが出来た件数ではない**。雲のまま4枚でも「5／10」と表示される。

★**`innerText` を「処理中」「Processing」で grep しても見つからない。**
雲は**テキストではなくアイコン**なので、文字列検査は**必ず0件＝緑**になる。
実際にこれで「処理中ゼロ・エラーゼロ」と誤って報告しかけた。

**正しい数え方（DOM で数える）**:

```js
// 枠ごとに「実際に描画されたサムネイル」を数える。
// 6 = プレビュー1 + スクショ5 が全部出来た状態。
[...document.querySelectorAll('img')]
  .filter(i => /mzstatic\.com\/image\/thumb/.test(i.src)).length
// ★全枠合計が (枠数 × 6) になるまでは未完。14/18 なら4枚が処理待ち。
```

★`アセットをチェック` ボタンは**検証ボタンではない**。
押すと「アセットライブラリから選ぶ」ダイアログが開くだけなので、
合否判定には使えない（キャンセルで閉じる）。

### ★実測で通った設定（2026-10-21）

公式の目標は 10-12Mbps だが、**27秒だと約19MB** になり
ブラウザ拡張の `file_upload`（10MB上限）では送れない。
★**2.09Mbps / 7.5MB で通った**（旧受理版は 3.2Mbps）。

```bash
ffmpeg -i IN.mp4 -vf "setsar=1"   -c:v libx264 -profile:v high -level 4.0 -pix_fmt yuv420p -r 30   -b:v 3220k -maxrate 3500k -bufsize 6000k -bf 2 -refs 1   -c:a aac -b:a 192k -ar 44100 -ac 2   -movflags +faststart -y OUT.mp4
```

★失敗したのは **1.27Mbps（crf 21）**。★`-b:v` で明示的に指定すること
（`-crf` だと静止画の多い画面録画では極端に低いビットレートになる）。

### ★枠は3つある（1つ入れて終わりにしない）

```
必須  Dynamic Island（中型ディスプレイ）  ← ここが空だと審査に出せない
任意  Dynamic Island（大型ディスプレイ）
任意  Face ID（大型ディスプレイ）
```

★**動画の対応サイズはどの枠も 886x1920 / 1920x886 で同じ**。同じファイルを使い回せる
（違うのはスクリーンショットのサイズだけ）。

**ブラウザ拡張の `file_upload` は 10MB が上限**

- 公式仕様（11Mbps）で作ると 27秒で約19MB になり**上限を超える**
- ⟹ 審査素材は**手でドラッグ&ドロップ**するのが確実
- ★画質を落として10MB以内にすると、保存失敗側に倒れる可能性がある

## 3.5 ★スクリーンショットも要る（必須枠は動画だけでは足りない）

必須枠（中型ディスプレイ）が **0/10** で空だと審査に出せない。

### 枠ごとにサイズが違う（★動画と違ってここは使い回せない）

| 枠 | スクショのサイズ | 撮影ビューポート（scale 3） |
|---|---|---|
| **中型**（必須） | **1179 x 2556** / 1206 x 2622 | **393 x 852** |
| 大型 Dynamic Island | 1290 x 2796 / 1320 x 2868 | 430 x 932 |
| 大型 Face ID | 1242 x 2688 / 1284 x 2778 | 414 x 896 |

★**動画は全枠 886x1920 で共通**なので使い回せるが、スクショは別物。

```bash
SCREENSHOT_ALLOW_NO_AUTH=1 SCREENSHOT_OUT_DIR=_store-assets/screenshots   node scripts/app/capture-appstore-screenshots.mjs
```

`capture-appstore-screenshots.mjs` の `DEVICES` に `iphone-61`（393x852）を足してある。

★`file_upload` は**複数ファイルを一度に送れる**（5枚で 2.4MB なら1回で済む）。

### ★`networkidle` を使わない（2つのスクリプトで同じ罠を踏んだ）

`page.goto(..., { waitUntil: 'networkidle' })` は**60秒でタイムアウトする**。
X の埋め込みが通信を続けるため idle にならない（curl では 2.4 秒で 200）。
⟹ `domcontentloaded` にして、読み込みは個別の待ちで担保する。

## 4. 返信（★素材を入れてから送る）

★**順序を守る**。素材を直す前に返信だけ送ると、Apple が実物を見に行って再却下される（v1.0.5 の前例）。

返信に書くこと:
- 指摘を認める（"You are correct"）。言い訳しない
- **何がダメだったか**を具体的に（例: マーケ用ムービーの切り出しでアプリ画面が無かった）
- **何に差し替えたか**を Apple の Next Steps の言葉で（"only use video screen captures of the app"）
- **全サイズで旧素材を消した**ことを明記
- ★実装していない機能に触れない

## ★やらないこと

- **BGM の出典が不明な音源を使わない**。審査素材に載せる前に作品番号を記録する
  （`_store-assets/app-preview/bgm/SOURCE.md` の型）
- **同じ操作を3回以上繰り返さない**。2回失敗したら原因を変えて試す
- **「たぶん処理中」で報告を締めない**。サムネイルが出たことを目で見てから「できた」と言う
